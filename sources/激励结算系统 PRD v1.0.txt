# 激励结算系统 PRD v1.0

Oct 13, 2026 · @Kerry CHU

**本系统是“只追加账本 + 配置化规则引擎 + 边缘处的 LLM”：先服务自家销售提成，再用同一架构接入其他公司的政策。** 外部研究有三条结论：开源项目可借鉴的是设计而不是代码；LLM 能起草规则，但金额必须由确定性引擎产出，并经示例用例和历史回放校验；行业标杆也把 AI 用在建计划、解释结算和校验数据上。

## 1. 外部研究与取舍

| 来源 | 研究事实 | 采用 | 不采用 |
| --- | --- | --- | --- |
| [OpenICM](https://github.com/kyssta-exe/OpenICM)（开源提成系统，AGPL-3.0） | 事件溯源、零依赖纯函数引擎、计划版本化、逐笔逐规则明细、争议流、GL 导出；但仓库仅 1 星、9 次提交，“功能全部完成”是自述 | 功能清单与测试用例参考 | 不引入代码：成熟度低；README 写明做托管服务需回馈修改 |
| [CaptivateIQ](https://captivateiq.com/ai-agents)（商用标杆） | 数据连接带生效日期、沙盒与克隆、直接/间接归因、拆分与覆盖、可追溯结算单、争议线程、审批；2026 年发布的 AI 代理用于[建计划、回答与校验、查算错](https://itbrief.co.uk/story/captivateiq-launches-ai-agents-for-compensation-planning)，仍为有限测试 | 需求基线；AI 的定位 | 不做无代码画布 |
| [GoRules ZEN](https://github.com/gorules/zen) | 开源规则引擎，JSON 决策模型与决策表，可嵌入 Node/Python/Go/Rust；函数节点会执行 JS | 候选的单笔条件层 | 禁止 LLM 生成函数节点 |
| [Formance Ledger](https://openapps.pro/apps/ledger) | 开源可编程双分录账本，幂等键，不可变日志；定位为独立金融服务 | 账本建模思路 | 不部署，量级不匹配，用 Postgres 约束实现 |
| [Catala 与 LLM 法条转代码研究](https://aclanthology.org/2025.nllp-1.4/) | LLM 把法条译成可执行代码被证明可行，评估依赖带单测的场景 | 用示例用例和回测评估 LLM 生成的规则 | 不引入该语言 |
| [Open Cap Format](https://github.com/Open-Cap-Table-Coalition/Open-Cap-Format-OCF) | 开源 JSON 股权数据标准，面向公司股权表 | P2 股权登记簿的数据结构参照 | 不用于计算；中国持股平台结构的适用性待验证 |
| 行业报告（经 [IT Brief](https://itbrief.co.uk/story/captivateiq-launches-ai-agents-for-compensation-planning) 转述） | 46% 的组织每季度调整提成方案，39% 仍要 1–2 个月才能完成调整 | 论证“政策到配置”值得做 |  |

## 2. 定位与范围

| 类别 | 内容 |
| --- | --- |
| 做 | 销售提成结算：计提、调整、冲销、关账、结算单；员工只读明细；规则与字段映射配置化；LLM 辅助起草与解释 |
| 只读取，不自建 | 员工与组织、CRM 成交、回款、合同、汇率；薪酬发放与个税由薪酬侧负责 |
| 后置 | 股权与期权域（第 16 节）；绩效数据汇总 |
| 不做 | AI 自动评分；AI 决定金额或归属；员工群聊作计算输入 |

**设计原则**：金额只由确定性引擎产出；账本只追加，更正都是新分录；每次计算同事务落快照；员工是有利益的一方，输入按“可能被操纵”设计；先回放历史，再谈实时。

## 3. 角色与权限

| 角色 | 目标 | 权限 |
| --- | --- | --- |
| 员工（销售） | 看懂每一笔 | 只读本人明细 |
| 销售主管 | 处理本团队异常 | 本团队只读，异常审批 |
| 规则 owner | 定规则与映射 | 编辑草案；不能审批结算单 |
| 财务 | 审批结算、对接发放 | 审批结算单；不能改规则 |
| 管理员 | 运维 | 无账本与快照的修改权 |
| 股权管理员（P2） | 登记授予、归属与行权，处理离职清单 | 仅限股权域，权限最严格，全部变更留痕 |

小公司可由负责人定规则、财务审批结算，二人分离即可。

## 4. 处理流程

1. **导入**：CRM 成交、回款、合同、汇率按映射配置进入标准事件，去重键保证幂等。
2. **校验**：数据质量问题进异常队列并附原始来源，不阻塞其他笔。
3. **计算**：规则版本加输入快照，经引擎纯函数得到分录与计算明细。
4. **异常**：命中阈值或归因存疑的笔进队列，由人裁决，裁决记为调整分录。
5. **关账**：Period 置为已关账，之后的更正只进下期调整。
6. **结算单**：按期生成快照，审批后导出。
7. **回执**：薪酬侧确认发放后回写，冲销据此对冲。

## 5. 数据模型

| 实体 | 关键字段 |
| --- | --- |
| Event（只追加） | id、类型、来源、payload、去重键、业务发生日、记录时间 |
| LedgerEntry | 员工、期间、类型（计提/调整/冲销/发放）、金额、币种、汇率与来源、关联分录、规则版本、快照 id |
| CalcSnapshot | 输入哈希与引用、规则版本、引擎版本、输出、计算过程 |
| RuleVersion | 规则配置、生效日期、状态、示例用例集 |
| FieldMapping | 源系统字段到标准结构的映射配置，同样版本化 |
| Period | 起止日期、状态（开放/关账中/已关账） |
| ApprovalTicket | 触发原因、金额、审批人、决定、时间 |
| SettlementSlip | 期间、员工明细、总额、版本、状态 |
| Plan / PlanVersion | 制度（销售提成、季度奖金、期权授予等）及其版本；版本含规则配置、适用范围、生效期、状态 |
| Assignment | 员工到制度版本的有生效期的关系；个人特批记在此，带原因与审批 |
| Pool / Allocation | 池子总额的计算结果，以及按岗位权重、系数、在岗天数分给个人的分配明细 |
| Grant / VestingSchedule / OptionPool（P2） | 授予、归属计划与每日归属事件、期权池余额；授予时锁定制度版本，只追加 |

- **三个时间**：业务发生日、记账日、规则生效日。追溯与更正靠它们区分。
- **必须表达的情形**：回款后计提、分期回款、退款与冲销、阶梯与累计达成、多人分单、外币、迟到与乱序事件、CRM 金额被改。
- **账本约束**：每笔分录成对记入“应付提成”和“提成费用”，数据库约束保证平衡且不可改删，参照 Formance 与 OpenICM 的做法。

## 6. 规则引擎与规则无关化

**6.1 原语集**（从自家政策里长出来，拿到其他公司政策后再补）

| 原语 | 说明 |
| --- | --- |
| 条件过滤 | 产品、区域、新老客、折扣等字段条件 |
| 费率与系数 | 固定比例、固定金额、系数相乘 |
| 阶梯 | 边际或整档，按单笔或按期累计 |
| 累计达成与加速 | 按期累计达成率触发不同费率 |
| 封顶与保底 | 封顶、draw、保障 |
| 拆分与覆盖 | 多人分成、主管覆盖 |
| 回款触发 | 回款后计提、分期、延迟 |
| 冲销 | 退款与取消的回溯期 |
| 币种换算 | 汇率来源与取值日 |
| 适用范围匹配 | 按岗位、级别、地区、团队、入职日期选人，范围本身版本化 |
| 池子与分配 | 先算池子总额，再按岗位权重、绩效系数、在岗天数分配，总和校验 |
| 期间折算 | 期间内换岗或换制度时按生效日期拆段，按在岗天数折算 |
| 时间归属 | 起始日、cliff、按月/季/年线性归属、里程碑、加速与暂停（P2，股权用） |

**6.2 执行分层**：单笔条件与系数用决策表层（ZEN 为候选）；阶梯、累计、拆分、冲销、关账由自写的薄层负责。第 1 周做 spike，通过标准是自家全部规则无需自定义函数即可表达；未通过则整套自写，引擎本身保持零数据库依赖。

**6.3 政策到配置**：上传政策文档、LLM 抽取结构化草案、系统列出澄清问题、人用示例确认、历史回测、影子运行、生效。产出是配置数据，不是代码；歧义和矛盾必须变成问题交给人，不允许自行补全。

**6.4 数据映射**：内部有固定的标准结构（成交、回款、客户、折扣、汇率），每家公司只配置字段映射。映射由 LLM 起草，人确认，回测验证。

**6.5 制度变更分级与指标**：制度变更是常态，按下表分级，只有第 3 类需要动代码。

| 级别 | 例子 | 处理 | 改代码 |
| --- | --- | --- | --- |
| 1 改参数 | 费率、门槛、封顶、配额、分配比例 | 新建规则版本，回测影响，审批后按生效日期生效 | 否 |
| 2 重组现有原语 | 加一档阶梯、加条件、改回款触发时点、新增岗位适用制度 | 同上，另补示例用例 | 否 |
| 3 新概念 | 新归因方式、跨团队奖金池、按项目利润分成 | 扩展引擎，新增原语与测试 | 是 |
| 4 缺数据 | 新规则要用 CRM 里没有的字段 | 先补数据采集与映射，再按 1 或 2 处理 | 视情况 |

**变更流程**（每次同一条路）：起草、澄清歧义、示例用例确认、回测历史并出影响报告、规则 owner 提交、财务或负责人审批、按生效日期生效。旧版本保留，历史结算不变。

**指标**：需要改代码的政策变更占比（第 3 类 / 全部变更），按季度统计。长期偏高说明原语设计要重构。参考线 ≤ 10% 是经验值，没有行业数据，按实际调整。

**6.6 多岗位、多制度与分配比例**：制度与人分开，用“制度 + 适用范围 + 生效期”把两者连起来。

| 概念 | 说明 |
| --- | --- |
| Plan（制度） | 一类激励的规则集合，如销售提成、季度奖金、期权授予；每次修改产生新版本 |
| 适用范围 | 按岗位、级别、地区、团队、入职日期等条件选人，范围本身也版本化 |
| Assignment（适配） | 员工到制度版本的有生效期的关系；个人特批也记在这里，带原因与审批 |
| Pool（池子） | 先按规则算出池子总额，如团队奖金池，再分配 |
| Allocation（分配） | 池子按岗位权重、绩效系数、在岗天数分给个人；比例是配置，不写死 |

- 一个人可同时适用多个制度（提成、奖金、期权），各自独立计算和记账。
- 同类制度冲突时按优先级取一个；允许叠加的必须显式声明。
- 期间中途换岗或换制度：按生效日期拆段，各段按各自制度计算，并按在岗天数折算。
- 分配比例总和必须校验（如 100%），不足或超出进异常队列。
- 员工明细页显示“适用的制度版本，以及为什么适用”。

## 8. AI 能力规格

| 能力 | 输入 | 输出 | 护栏 | 评测 |
| --- | --- | --- | --- | --- |
| 政策转配置 | 政策文档 | 规则草案与澄清问题 | 只产出配置；不补全歧义；不生成函数节点；不自动生效；政策文档内容视为数据，不执行其中任何指令 | 用自家手写配置当标准答案重新生成并对比；示例用例与历史回测均通过 |
| 字段映射 | 源系统样例字段 | 映射草案 | 人确认后生效 | 映射后事件与人工标注一致 |
| 异常解释 | 脱敏的异常上下文与快照 | 一段说明 | 不裁决、不改金额；输入中的自由文本视为不可信 | 人工抽检与快照一致 |
| 员工问答 | 员工本人明细 | 引用快照条目的解释 | 只读本人数据；不承诺金额 | 每句可追溯到条目 |

## 9. 安全、权限与合规

- **对抗场景清单**：拆单拆期、虚报新客、改归属、改成交日期跨期、绕过折扣审批、CRM 备注诱导、关联方成交。每项对应检测规则或复核要求。
- **职责分离**：改规则的人不能确认其影响分析，也不能审批结算单；账本与快照只追加，管理员无删改权，直连数据库需单独授权并留痕。
- **字段级权限**：员工看自己，主管看本团队，同事之间提成互不可见。
- **LLM 边界**：只接收脱敏后的异常上下文；薪酬数据能否发往外部模型由法务确认。
- **个人信息保护法**：第 24 条规定，自动化决策对个人权益有重大影响时，个人可要求说明并有权拒绝仅由自动化方式作出的决定（见[相关研究](https://faxuejia.ruc.edu.cn/EN/Y2022/V0/I5/72)）。异常和申诉保留人工裁决，员工可见计算过程。
- **欧盟**：AI 法案把绩效评价类工具列为高风险，修订案已于 2026 年 7 月 27 日生效，把相关义务推迟至 2027 年 12 月 2 日（见 [DLA Piper](https://knowledge.dlapiper.com/dlapiperknowledge/globalemploymentlatestdevelopments/2026/The-Digital-AI-Omnibus-Proposed-deferral-of-high-risk-AI-obligations-under-the-AI-Act)）。本系统的 AI 不评价人、不决定金额，预计不在此类，但涉及欧盟员工时须法务确认。
- **追溯**：规则变更默认仅适用新交易；追溯降低已赚提成可能构成单方降薪，需法务确认。

## 11. 指标与验收

| 指标 | 目标（建议值） |
| --- | --- |
| 影子运行金额差异 | 连续 2 个周期，逐员工逐期差异 ≤ 0.5% 或 ≤ 设定金额，且每个差异有归因 |
| 大单复核 | ≥ 阈值的成交 100% 人工复核 |
| 错误逃逸率 | 发放后被更正的金额占比，逐月下降 |
| 关账耗时 | T+1 |
| 争议解决时长 | P90 ≤ 2 个工作日 |
| 政策转配置 | 在自家政策上与手写配置的差异为零或全部可解释 |
| 政策变更需改代码占比 | 按季度统计，参考线 ≤ 10%（见 6.5） |
| 黄金用例 | 100% 通过，每次改动都跑（附录 C） |

差异归因分四类：规则缺口、数据错误、人工历史错误、系统缺陷。前三类不算系统失败，但必须逐条关闭。

## 12. 路线图（约 16 周，建议值）

| 阶段 | 周期 | 交付 | 退出标准 |
| --- | --- | --- | --- |
| 1 历史回放 | 第 1–4 周 | 导入 3–6 个月成交与回款；规则引擎 spike 与自家规则；与人工历史结算逐员工对比 | 差异报告完成；规则缺口清单经确认；准确率基线建立 |
| 2 影子运行 | 第 5–10 周 | 账本、快照、关账；异常队列与审批；员工只读明细；制度与岗位适配；财务导出 | 连续 2 个周期差异达标；大单全复核；安全与职责分离验收通过 |
| 3 正式切换 | 第 11–16 周 | 政策转配置、字段映射草案、回测影响分析；当期正式结算 | 一个完整周期按系统结算；关账 T+1；无高优先级未关闭差异 |
| 4 验证与扩展 | 之后 | 用 2–3 份其他公司政策验证原语集；申诉工作流；回执回写；股权与期权域（第 16 节） | 需新增原语的政策占比可接受后，才启动多租户与自助上传 |

## 13. 技术选型

- TypeScript 单体加 Postgres，与自建 CRM 同栈；引擎为零数据库依赖的纯模块。
- 事件、账本、快照同库同事务，用 outbox；不引入事件流平台、图数据库和 Agent 框架。
- 前端先做员工只读页与管理台，规则以决策表视图编辑。
- LLM 只经服务端调用，带调用日志与额度。

## 14. 与 v9.0 的取舍

**保留并改造**：规则版本化与影响分析（改为历史回放）；证据链（改为计算快照）；审批分级（改为金额与规则类型阈值）；计算与发放解耦；数据最小化与权限；LLM 成本控制（改为额度与日志）。

**完全舍弃**：六类 Agent 与“无中央调度”；监督容量模型与 L0–L5 分级；独立证据图；“单笔 P95 5 分钟、1000 事件/秒”目标；“一次通过率”北极星；飞书群聊作输入；AI 绩效评分；token 级成本章；事件流平台。

## 15. 风险与开放问题

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 自用规模小，只能验证流程，验证不了规则无关化 | 高 | 尽早拿 2–3 份其他公司政策文本；验证前不启动多租户 |
| 规则无 owner，例外越积越多 | 高 | 指定 owner；每季度清理例外 |
| CRM 数据质量差 | 高 | 影子运行暴露问题；必填校验 |
| LLM 生成规则语义错误 | 高 | 示例用例、回测、影子运行三道关；不自动生效 |
| 追溯引发劳动争议 | 高 | 默认仅新交易；追溯需法务 |
| 开源许可风险 | 中 | 不引入 AGPL 代码；ZEN 许可证在 spike 时确认 |
| 制度与岗位组合增多，配置难维护 | 中 | 制度模板化；适用范围用条件而非逐人名单；每季度清理失效制度与个人特批 |
| 股权与期权涉及法律、税务和外汇，复杂度远高于提成 | 高 | 系统只做登记、归属计算与审批，不做估值、税务和法律文件；P2 启动前由法务与顾问确认边界 |
| 制度更新单方损害已授予权益 | 高 | 已授予权益按授予时的制度版本冻结；不利变更须走法务确认的路径 |

**开放问题**：现有提成规则样例（条数、例外数、维护人）；上月结算表与对应成交回款数据（可脱敏）；薪酬与财务侧现状（系统或 Excel）；审批与大单阈值；追溯类变更的法务流程；自用销售团队的真实规模；成交与回款的事实源是哪个系统（HubSpot 还是自建 CRM，回款记在哪里）。

## 16. 股权与期权（扩展域，P2 起步）

**股权期权与提成是两类问题**：提成是交易驱动的计算；股权是带法律文件的登记簿，加上时间驱动的归属日历。系统只做登记、归属计算、查询与审批，不做估值、税务和法律文件。

| 范围 | 内容 |
| --- | --- |
| 做 | 授予登记、归属计划与日历、行权记录、期权池余额、授予与行权审批、员工自助查询、法律文件的引用（只存位置和编号） |
| 不做 | 估值、税务计算、法律文件起草、股东会与董事会决议、工商与外汇登记 |

**岗位差异**：授予政策按岗位和级别给出授予区间、归属计划、行权规则、离职处理，和提成制度一样版本化。授予时锁定当时的制度版本。

**归属引擎**：确定性、时间驱动，复用第 6 节的版本与回放能力。支持起始日、cliff、按月/季/年线性归属、里程碑（由人确认达成）、加速条件、暂停（如休假，按制度）。每日跑批生成归属事件，写入只追加的授予台账。

**期权池**：总量、已授予、已归属、已行权、已失效、可用余额。任何授予先校验余额，持股比例按全稀释口径查询。

**离职与回购**：按授予时的制度版本，系统生成未归属失效、已归属行权窗口、回购的清单，金额与比例由条款决定，由人审批。

**制度更新**：已授予权益按授予时的版本冻结，新制度只用于新授予；对已授予权益做不利变更需要协商，路径由法务确认。

**持股平台与跨境**：间接持股（如有限合伙）的映射、外汇与税务登记由法务和顾问负责；数据结构先参照 OCF 的股权类别、已发行、全稀释等概念，不强求一致。

**权限**：权益数据最敏感，员工只看本人，全表只开放给极少数授权角色，全部变更留痕。

**补充开放问题**：岗位清单与各岗位适用的制度；期权池与授予政策现状；是否有持股平台；归属条件是否含绩效或里程碑。

## 附录 A：事件处理规则

**以下规则让 DATA-001 和 LEDGER-001 的“均有处理规则”可执行。** 原则：事件只追加，到达顺序只决定记账日，不决定计算结果。

| 情形 | 处理 | 账本效果 |
| --- | --- | --- |
| 重复事件（同去重键） | 丢弃并记一条重复日志 | 无 |
| 迟到事件（业务日在已关账期间） | 业务日保持原日期，记账日为当前期 | 当期调整分录，员工明细标“补记” |
| 修订事件（金额或归属被改） | 保留原事件，新增修订事件引用原事件，重算受影响的笔 | 当期调整分录，只记差额 |
| 撤销事件（成交取消、回款退回） | 新增撤销事件引用原事件 | 按冲销规则出冲销分录 |
| 乱序事件 | 按业务日期计算，不依赖到达顺序 | 同上 |
| 数据缺失或校验失败 | 进异常队列，不计提 | 无，待人处理 |
| 汇率缺失 | 进异常队列 | 无 |
| 关账后规则版本变更 | 已关账期间不受影响 | 无 |

**政策参数（系统必须在政策解析时提问，不得默认）**：已关账期间的迟到事件，阶梯取“补记所在期的累计”还是“回算原期”（建议默认前者，不重开已关账期间）；冲销是否同步回退累计；汇率取回款日、合同日还是月初。

## 附录 B：状态流转

| 对象 | 流转 | 约束 |
| --- | --- | --- |
| Period | 开放、关账中、已关账 | 关账中冻结输入并做最终计算与对账；已关账不可回退，回退只允许关账中到开放，需负责人权限并留痕 |
| RuleVersion | 草稿、回测中、待审批、生效、已停用 | 生效后不可改，只能新建版本；审批人不能是提交人 |

| SettlementSlip | 草稿、待审批、已批准、已导出、已发放 | 已批准后发现错误：作废并生成新版本，旧版本保留；已发放以回执为准 |

## 附录 C：黄金用例（P0 验收，示例数字仅用于说明语义）

**示例政策**：提成在回款时触发；按员工本人当季累计回款额做边际阶梯，0–100 万 5%，100–200 万 7%，200 万以上 10%。以下数字不代表你们的实际政策，上线前用自家规则替换，但这些语义都要覆盖。

| 编号 | 场景 | 输入 | 期望结果 | 验证的语义 |
| --- | --- | --- | --- | --- |
| G1 | 跨档 | 累计 80 万，本笔回款 40 万 | 20 万×5% + 20 万×7% = 24,000 | 边际阶梯 |
| G2 | 分期回款 | 合同 60 万，先回 40 万再回 20 万，累计起点 0 | 20,000 + 10,000 = 30,000，与一次回 60 万相同 | 回款触发，分期不改变结果 |
| G3 | 退款冲销 | 接 G1，次月客户退款 10 万 | 按该笔平均费率 6%（24,000÷40 万）冲销 6,000，记在次月，原分录不改 | 冲销只追加；累计是否回退由政策参数决定 |
| G4 | 分单 | 回款 10 万，A 占 60%，B 占 40%，两人累计均在第一档 | A 3,000，B 2,000 | 拆分，各按自己的累计适用阶梯 |
| G5 | 外币 | 回款 50,000 美元，汇率取回款日 7.10（示例），第一档 | 355,000 元×5% = 17,750，分录记人民币、汇率及来源 | 币种换算可追溯 |
| G6 | 迟到事件 | 9 月 28 日回款 30 万，10 月 3 日才到，9 月已关账，10 月累计为 0 | 15,000，业务日记 9 月 28 日，记账进 10 月调整分录，明细标“补记” | 迟到不重开已关账期间 |
| G7 | 重复事件 | 同一笔回款推送两次 | 只计提一次 | 幂等 |

## 附录 F：测试与切换

**测试**

- 黄金用例（附录 C）：每次改动都跑，必须全部通过。
- 回放一致性：同一区间、同一规则版本、同一输入连跑两次，分录逐条一致。
- 属性测试：随机打乱事件到达顺序、随机重复投递，期间汇总结果不变（附录 A 的原则）。
- 规则回归：每次规则变更重跑全部示例用例，并与上一版本逐笔对比。
- 影子运行：连续 2 个周期与人工结算对比（第 11 节）。
- 对账自检：每日自动运行（第 10 节）。

**切换与回滚**

- 切换条件：影子运行达标，财务与负责人签字确认。
- 回滚：发现系统性错误时，当期退回人工结算；系统账本保留，已发放的错误用冲销分录更正，不删记录。
- 切换后第一个周期保留人工抽查，再逐步取消。
