# 一、总体评审

## 1. 这份 PRD 做对了什么

### ① 产品定位已经从内部工具升级为可产品化系统

文档明确提出从 Anari 内部制度执行系统转向制度无关的 AI-native 绩效与激励操作系统，并将 Anari 的具体制度作为首个租户的配置实例。

这是正确的产品架构方向。

它意味着产品核心不应该是某家公司的一套绩效计算公式，而应该是可复用的能力：

- 任意企业的指标、权重、考核周期和评分规则均可配置。
- 不同企业可以使用不同的奖金、提成和任务悬赏制度。
- 评价、激励计算、审批、员工确认、申诉和结算形成完整闭环。
- AI 能够分析历史数据，发现制度缺陷，并提出改进建议。

**关键判断：制度无关不能只体现在配置表里，还必须贯穿规则引擎、工作流、权限体系、数据模型和测试体系。**

如果只是把 Anari 的公式抽象成几个配置项，仍然不是真正的制度无关产品。

### ② 坚持金额计算与 LLM 隔离，是正确的底层原则

PRD 明确规定金额计算必须使用确定性规则引擎，LLM 不得写入金额字段，并要求独立对照实现验证计算结果。

这一原则应当保留，不建议妥协。

绩效激励系统与普通 AI 应用有一个本质区别：AI 给出的评价可以由人复核，但激励金额一旦出错，就可能直接造成财务损失、员工争议和管理信任崩塌。

建议将其升级为四层保障：

| 保障层 | 应当实现的能力 |
|---|---|
| 规则定义 | 公式、条件、门槛、舍入规则均有明确语义 |
| 确定性执行 | 同一输入快照与规则版本必然得到相同结果 |
| 独立验证 | 通过独立实现、边界测试和属性测试发现错误 |
| 结算控制 | 未通过校验、审批或对账的结果不能进入正式结算 |

还需要注意：**独立对照实现与主引擎使用相同的错误业务假设时，两边即使结果完全一致，也不代表结果正确。**

因此，除了双引擎对账，还需要由业务负责人确认的基准案例、边界案例和历史案例。

### ③ 证据图谱是合理的核心数据层

PRD 将 EvidenceNode 作为跨系统事实接口，要求评价结果可以追溯到证据，并规定事实修正通过冲销或更正事件处理。

这比简单地把飞书任务、CRM 订单和人工评分拼成一张报表更合理。

例如，销售人员的绩效评价可能涉及：

- 客户开发与跟进记录。
- 报价和订单。
- 实际回款。
- 项目交付。
- 客户投诉或服务质量。
- 个人实际贡献与团队协作。

这些事实的来源、时间、归属和可信度都可能不同。

证据层的价值在于，让系统能够回答：

1. 这个评价为什么产生？
2. 它依据了哪些业务事实？
3. 事实来自哪个系统？
4. 事实是否经过确认？
5. 如果事实发生更正，哪些评价和金额需要重新计算？

不过，当前 PRD 对证据的定义仍然不够深入，后面会重点讨论。

### ④ 已经意识到 Agentic 不等于增加聊天机器人

PRD 不只是要求 AI 生成评语，还涉及主动生成评价草稿、提出悬赏推荐、分析制度健康度，以及在人工确认后执行相关流程。

它还提出自主权分级、意图预览、行动审计和 AI 关闭后的人工降级能力。

这些设计方向是正确的。

但需要进一步回答一个关键问题：

**Agent 究竟只是生成建议，还是能够感知业务状态、主动规划任务、调用工具、跟踪执行结果，并在失败时恢复？**

这将决定系统最终是一个带 AI 的绩效管理软件，还是一个真正的 Agentic 绩效与激励操作系统。

# 二、当前 PRD 最重要的八个问题

以下是我认为最值得优先解决的问题，按对产品成败的影响排序。

## P0-1：业务规则还没有达到可执行、可验证的程度

这是最高优先级的问题。

PRD 已经列出规则引擎的 DSL 原语，包括加权、阶梯、封顶保底、按比例分池、门槛、收敛、抵扣和币种换算。

但这些名称并不等于规则定义已经完成。

例如，假设企业采用如下激励规则：

- 销售额达到目标的 80%，开始计提奖金。
- 达到目标的 100%，适用标准提成率。
- 超额完成后，采用阶梯提成。
- 季度奖金受到公司可分配利润的约束。
- 已退款的订单需要冲销之前确认的提成。

开发团队仍然需要知道：

- 销售额按签约额、发货额还是实际回款计算？
- 目标完成率如何计算？
- 目标值为零或缺失时怎么办？
- 阶梯区间采用左闭右开还是其他边界约定？
- 超额部分采用增量提成率还是全部金额适用新提成率？
- 利润不足时，如何在多人之间分配有限奖金池？
- 退款发生在下个季度时，冲销哪个周期的提成？
- 多种激励同时满足条件时，优先级是什么？
- 币种转换、汇率精度和最终金额舍入如何处理？

如果这些问题留给开发人员自行判断，最后很容易出现一种危险情况：系统可以正常运行，计算结果也看起来合理，但实际执行的并不是管理层批准的制度。

### 我的建议

新增一份独立于主 PRD 的《激励规则语义与计算规范》。

至少包括：

| 规范 | 必须明确的内容 |
|---|---|
| 输入数据 | 来源、字段含义、单位、完整性和可信度 |
| 计算顺序 | 指标计算、资格判定、门槛、提成、奖金池分配、抵扣 |
| 数学语义 | 公式、边界条件、精度和舍入 |
| 数据缺失 | BLOCKED、NEEDS_REVIEW 等状态的触发条件 |
| 版本语义 | 生效日期、历史追溯和重新计算规则 |
| 结果解释 | 每一笔金额的计算过程与业务依据 |
| 测试规范 | 标准案例、边界案例、异常案例及预期结果 |

建议要求每条规则都能够转化为可执行测试。

**验收标准不应该只是“公式测试集全通过”，而应该是：每条业务规则都有明确语义、基准案例、边界案例和可重复执行的验证结果。**

## P0-2：证据图谱缺少最关键的归属与因果语义

当前 EvidenceNode 包含事实类型、主体、对象、来源、事件 ID、置信度、完整度和时间戳。

这些字段是必要的，但不足以支撑可信的绩效归因。

例如，一个销售订单可能由销售、技术支持、产品经理和供应链人员共同完成。

如果系统只知道某个人参与过一个任务，就无法合理地判断该订单的结果应该如何归属。

类似问题还包括：

- 一项成果究竟属于个人、团队还是跨部门项目？
- 多个人对同一成果的贡献如何记录？
- 任务完成是否等于业务结果实现？
- CRM 中的订单金额是否已经回款？
- 一条人工填写的工作日志是否足以证明绩效贡献？
- 同一事实在飞书和 CRM 中重复出现时，如何识别？
- 事实被更正后，哪些评价与激励结果需要失效或重算？

### 我的建议

将证据图谱从单纯的事实集合升级为包含关系、归属和血缘信息的证据体系。

建议至少明确以下概念：

| 概念 | 作用 |
|---|---|
| Evidence | 原始或经过确认的业务事实 |
| EvidenceSource | 来源系统、记录 ID、采集方式 |
| EvidenceRelationship | 人、任务、交付物、订单和结果之间的关系 |
| ContributionClaim | 员工对某项贡献的申报 |
| AttributionDecision | 经确认的贡献归属与分配 |
| EvidenceCorrection | 更正、冲销及其影响范围 |
| EvidenceSnapshot | 某一考核周期实际采用的证据集合 |

其中，ContributionClaim 不应该直接变成已确认的绩效事实。员工申报、系统识别和管理者确认应当是不同的状态。

还需要特别注意：

**证据可信度不等于贡献程度。**

一个订单的回款事实可能具有很高的可信度，但它不能直接证明某个员工对该订单贡献了多少。

这两个维度必须分别建模。

## P0-3：评价 Agent 缺少可验证的评价质量控制机制

PRD 要求评价草稿中的每个观点都挂载证据，且证据挂载率达到 100%。

这是一项必要条件，但不是充分条件。

一条评价完全可以引用真实证据，却得出错误结论。

例如：

> 某员工本季度参与了 20 个项目，因此其协作能力优秀。

即使 20 个项目都是真实记录，也不能直接证明协作能力优秀。

系统还需要知道：

- 该员工承担什么职责？
- 项目结果如何？
- 员工在项目中做了什么？
- Rubric 如何定义优秀？
- 哪些证据支持或反驳该判断？
- 是否存在缺失数据或其他解释？

### 我的建议

为评价 Agent 建立一套独立的质量控制机制。

**第一层：评价依据验证**

- 所引用的证据必须真实存在。
- 引用内容必须支持对应的评价观点。
- 评价必须符合当前版本的 Rubric。
- 不允许把相关性直接当作因果关系。
- 不允许因为没有数据就默认员工表现差。

**第二层：评价完整性检查**

- 检查必要指标是否缺失。
- 检查正面和负面证据是否均被考虑。
- 检查是否存在重复计数。
- 检查跨周期、跨岗位和跨职责比较是否合理。
- 无法形成可靠判断时，应允许输出“证据不足”。

**第三层：评价质量监控**

- 评价与 Rubric 的符合度。
- 证据支持率及不支持的观点比例。
- 管理者修改幅度。
- 员工异议率。
- 申诉后被推翻的比例。
- 不同岗位或群体间的系统性偏差。

其中，采纳率只能作为诊断信号，不能直接代表评价质量。

PRD 已经提出采纳率超过 95% 时触发“橡皮图章”审查，这是一个有价值的反向指标，但还应结合独立复核结果，避免把低采纳率误判为 AI 质量高。

## P0-4：从评价结果到最终结算的状态机不完整

PRD 定义了评价草稿、确认、员工确认或异议、激励计算和结算导出等环节。

但真实业务中，流程不会总是顺利完成。

例如：

- 员工对评价提出异议，但奖金结算截止日期已经到达。
- 管理者在确认后发现订单金额错误。
- 财务发现回款数据与银行流水不一致。
- 绩效周期结束后发生订单退款。
- 员工离职，但仍有尚未确认的提成。
- 规则版本在周期中途发生变化。
- 某个审批人同时是被考核对象。
- 系统重复收到同一条结算请求。

如果没有完整的状态机，这些情况很容易依赖人工操作数据库或临时修改记录解决。

### 我的建议

至少建立以下相互关联的状态机：

| 对象 | 建议状态 |
|---|---|
| 考核周期 | 草稿、数据汇集、待评价、待审核、待员工确认、异议处理中、已锁定、已关闭 |
| 评价结果 | 草稿、待审核、已确认、异议中、已复核、已撤销 |
| 激励试算 | 未计算、计算中、计算成功、阻断、待复核 |
| 金额账本 | 待审核、已批准、已锁定、已冲销 |
| 结算批次 | 待生成、待对账、待批准、已导出、已回写、已关闭 |

这些只是建议的起始设计，不是要求把所有状态机械地塞进一个统一状态字段。

更重要的是定义每个状态的转换条件、执行权限、失败恢复策略和审计要求。

例如：

**员工提出异议，不应该直接修改已经确认的金额账本。**

系统应该创建异议案件，保留原始版本，并在复核通过后按明确规则生成新的计算版本或调整记录。

## P0-5：悬赏市场与传统绩效制度之间的边界尚不清楚

PRD 将悬赏列为 P0，并设计了发布、认领、协商、验收和支付流程。

同时，悬赏被定位为针对超出本职工作的额外贡献，允许租户配置是否开放本职专项悬赏，并要求检测跨激励类型的重复计奖。

这是一个值得探索的方向，但也会显著扩大首版系统的复杂度。

悬赏涉及的并不只是一个新的激励类型，还涉及：

- 任务发布权限。
- 预算预占与释放。
- 多人协作和成果归属。
- 交付物验收标准。
- 争议处理。
- 悬赏取消或延期。
- 重复认领与重复支付。
- 与岗位职责和绩效考核的关系。

尤其是“同一成果重复计奖检测拦截率 100%”，目前缺少可以直接实施的判断规则。

例如，同一项目既产生销售提成，又产生技术团队的专项奖金，不一定就是重复计奖。真正需要识别的是：**哪些激励针对同一项贡献、同一个计奖对象和同一个业务结果，并且按照制度不允许重复支付。**

### 我的建议

把重复计奖检测分成两类：

1. **确定性冲突检测**：使用成果 ID、业务对象、计奖对象、激励规则和时间范围识别明确的重复计奖。
2. **潜在重复计奖检测**：利用语义匹配识别可能存在重叠的成果，由人工复核。

第一类可以作为硬性阻断规则；第二类应该输出风险提示，而不是直接判定违规。

对于首个内部版本，我倾向于保留悬赏的完整数据模型与规则接口，但要谨慎控制其开发范围。

如果悬赏是公司未来核心产品差异化能力，就可以保留在 P0；如果当前首要目标是先跑通真实绩效与激励结算，则应考虑分阶段交付悬赏市场。

## P0-6：多租户与权限安全的设计还不够具体

PRD 已经提出 tenant_id、行级隔离、字段级权限、数据范围隔离和审计日志。

但这些原则不能直接证明系统安全。

尤其是绩效激励系统，权限错误可能导致员工薪酬、评价和申诉信息泄露。

建议至少明确：

- 每个数据库查询是否强制绑定租户上下文。
- 是否存在跨租户查询和写入的自动化测试。
- Agent 工具是否使用独立服务身份。
- Agent 能否通过自然语言问答间接获得越权数据。
- 导出文件、缓存、日志和异步任务是否同样执行权限检查。
- 员工离职、组织调整或管理关系变化后，历史数据权限如何处理。
- 财务是否能查看评价细节，管理者是否能查看财务敏感字段。
- 审计日志如何防篡改、备份和恢复。

建议在数据库、服务层和工具调用层实施纵深防御，而不是仅依赖前端隐藏按钮。

另外，PRD 将行级隔离与独立 Schema 作为待确认事项。这里不应该只依据开发便利性作决定，还应考虑客户数据敏感度、部署方式、备份恢复和商业化客户的安全要求。

## P0-7：合规设计方向正确，但不能把告知书当作完整合规方案

PRD 提出了中国个人信息保护、欧盟 AI Act、员工告知、人工监督、日志留存和异议渠道等内容。

但实际合规义务取决于产品部署地、客户身份、使用场景、数据处理角色以及具体功能。

特别是涉及员工评价、绩效分数和激励决策时，需要分别评估：

- 自动化处理的法律依据。
- 员工告知与相关权利。
- 个人信息处理的必要性与最小化。
- 对员工产生重大影响的自动化决策。
- 人工审核是否具有实质性，而非形式上的点击确认。
- 跨境数据传输和模型供应商处理。
- 评价结果的保存期限和删除限制。
- 不同国家和地区的劳动法及员工代表参与要求。

因此，不能仅凭员工签署告知书，就认定系统满足全部法律要求。

此外，PRD 中关于欧盟 AI Act 的适用范围、生效时间及具体义务，应在产品正式面向欧盟市场前，由专业法律顾问根据最新法规文本和实际业务场景核验。

工程上则应将合规要求转化为具体能力，例如：

- 按法域配置的数据处理规则。
- 可导出的决策依据与人工审核记录。
- 申诉、复核和更正流程。
- 数据保留与删除策略。
- 可追溯的模型和规则版本。
- 对高影响决策的权限限制。

## P0-8：十周路线图可能低估了真实交付复杂度

PRD 计划在 W0–W10 完成从架构盘点、数据接入、规则引擎、评价 Agent 到影子考核和真实考核的过程。

如果团队已有成熟的基础代码、稳定的飞书与 CRM 接口，以及经过确认的制度规则，十周完成一个严格限定范围的内部 MVP 并非完全不可能。

但如果需要从头构建：

- 证据图谱。
- 多源数据同步。
- 声明式规则引擎。
- 独立计算对照。
- 完整权限体系。
- 评价 Agent。
- 申诉与确认工作流。
- 悬赏市场。
- 合规基础设施。
- 完整的结算闭环。

那么十周计划就存在明显的交付风险。

尤其是影子考核周期必须与真实业务周期相匹配。如果制度涉及季度奖金，无法仅凭一个月的开发计划就证明完整季度计算和冲销逻辑可靠。

### 我的建议

将项目里程碑改成以业务能力和风险关闭为中心，而不是单纯以周数为中心。

**里程碑 A：确定性计算可信**

完成规则语义、数据快照、计算引擎、独立验证和历史回放。

**里程碑 B：绩效评价可信**

完成证据归属、Rubric、评价草稿、人工复核和申诉闭环。

**里程碑 C：结算闭环可信**

完成激励试算、审批、金额锁定、结算导出、对账和冲销。

**里程碑 D：Agentic 能力验证**

完成主动识别异常、创建待办、推动处理、跟踪结果和失败恢复。

**里程碑 E：真实业务试运行**

完成至少一个与实际考核周期相匹配的影子运行，并满足预先定义的质量与风险门槛。

这些里程碑可以并行推进，但必须设置明确的退出条件。

# 三、AI-native 与 Agentic 能力：目前最大的升级空间

如果只看常规企业软件能力，这份 PRD 已经覆盖了不少核心模块。

但如果目标是打造具有竞争力的 AI-native 绩效与激励操作系统，我认为目前最需要升级的部分是 Agent 的执行闭环。

现有设计已经有评价 Agent、洞察 Agent、申报辅助和悬赏匹配。

然而，这些 Agent 主要还是围绕生成内容、提供建议和辅助决策。

真正的 Agentic 系统还应该具备以下能力。

## 1. 从被动问答升级为主动发现问题

例如，系统发现：

- 某个销售的订单已回款，但 CRM 中的绩效归属尚未确认。
- 某项任务已完成，却没有对应的交付物或验收证据。
- 某个部门的目标完成率明显异常。
- 某员工的绩效评价缺少必要证据。
- 某笔奖金受到退款或坏账事件影响。
- 某个管理者长期未完成确认任务。

系统不应该只是等待用户询问，而应该主动识别异常，形成待处理事项。

## 2. 从生成建议升级为推进任务完成

建议增加一个受控的工作流协调层。

例如：

1. 发现订单回款与绩效记录不一致。
2. 检查两个系统中的原始数据。
3. 判断问题属于缺失、冲突还是延迟同步。
4. 自动收集相关证据。
5. 创建待办并指派给有权限的责任人。
6. 设定处理期限。
7. 跟踪处理结果。
8. 重新验证数据。
9. 更新考核准备状态。
10. 将最终结果和处理过程写入审计记录。

其中，AI 可以负责识别、规划、证据收集和推动处理；涉及绩效事实认定、规则修改或金额生效的动作，仍应遵循相应的审批制度。

这才是一个可以衡量业务价值的 Agentic 闭环。

## 3. 从单一 Agent 升级为有边界的多 Agent 协作

建议将职责划分为以下逻辑角色：

| Agent | 主要职责 | 权限边界 |
|---|---|---|
| Data Quality Agent | 发现缺失、冲突、延迟和重复数据 | 不直接修改已确认的业务事实 |
| Evaluation Agent | 基于证据与 Rubric 生成评价草稿 | 不决定最终绩效 |
| Incentive Analysis Agent | 解释试算结果、发现异常和潜在规则冲突 | 不计算或写入正式金额 |
| Workflow Agent | 创建任务、提醒责任人、跟踪审批 | 不绕过审批或授权 |
| Appeal Support Agent | 整理申诉材料、证据和规则依据 | 不裁决自己的案件 |
| Policy Insight Agent | 分析制度效果并提出改进建议 | 不自动修改正式制度 |

这里的多 Agent 不应该意味着必须运行六个独立模型。

初期完全可以使用共享模型和统一工具平台，通过不同的任务定义、上下文隔离、权限策略和工作流实现这些职责。

**核心不是 Agent 数量，而是职责边界清晰、执行过程可追溯、失败后可以恢复。**

## 4. 将自主权分级从概念变成可执行策略

PRD 已经提出 L0–L3 自主权分级。

但还需要为每种操作定义：

- 允许的工具。
- 允许读取的数据范围。
- 允许写入的对象。
- 是否需要人工批准。
- 是否允许撤销。
- 失败时如何处理。
- 哪些事件必须升级给人。

例如，系统可以自动发送考核提醒，但不应该因为某个 Agent 的采纳率很高，就自动获得修改奖金规则或确认员工绩效的权限。

**自主权应该按动作风险授权，而不是只按 Agent 整体成熟度授权。**

# 四、建议补齐的数据模型与技术架构

除了前面提到的 Evidence 体系，我认为至少还需要补充以下关键设计。

| 建议补充的对象 | 主要目的 |
|---|---|
| SourceSyncRun | 记录每次数据同步、失败、重试和水位 |
| DataQualityIssue | 统一管理缺失、冲突和重复数据 |
| ContributionClaim | 记录员工申报的贡献及审核状态 |
| EvaluationSnapshot | 固定评价时实际使用的规则、证据与输入 |
| CalculationRun | 记录计算请求、执行状态、版本和输入输出哈希 |
| SettlementBatch | 管理正式结算批次、对账和导出 |
| AdjustmentRecord | 记录补发、扣回、冲销和更正 |
| WorkflowRun | 记录 Agent 或业务工作流的执行进度 |
| ApprovalDecision | 记录审批人、决策、理由及其依据 |
| ModelEvaluationRun | 记录评价模型的离线测试、回归测试和质量结果 |

这些对象不一定都需要成为独立数据库表，但必须明确其数据契约、生命周期和责任边界。

还建议增加以下系统级要求：

- 异步任务具备幂等、重试、超时和死信处理。
- 数据同步支持断点恢复与定期对账。
- 所有计算结果可以根据输入快照和规则版本重现。
- 规则升级必须支持历史回放和差异解释。
- 审计日志与业务数据修改机制分离。
- 重要操作具备事务边界与失败补偿机制。
- 对关键链路设置延迟、失败率和数据完整性监控。

尤其需要明确一点：

**可追溯不等于可重现。**

仅仅保存输入快照哈希并不能重现历史计算；系统还必须保存或能够恢复实际输入、规则版本、汇率来源、必要的计算参数，以及相关的执行版本。

# 五、产品范围应该如何收敛

我不建议现在继续无限扩展功能。

当前 P0 已经同时包含证据图谱、多个系统集成、指标库、周期引擎、规则引擎、评价 Agent、悬赏市场、洞察 Agent、合规、权限和完整结算流程。

对于首个内部版本，建议按以下顺序推进。

### 第一阶段：先把计算和结算做可信

必须交付：

- 指标与制度配置。
- 必要的数据接入。
- 数据完整性检查。
- 确定性规则引擎。
- 独立计算对照。
- 计算快照和审计。
- 激励试算、审批与结算导出。

### 第二阶段：完成评价闭环

增加：

- Rubric 配置。
- 评价 Agent。
- 证据依据展示。
- 管理者实质审核。
- 员工确认、异议和申诉。
- 评价质量监控。

### 第三阶段：建设 Agentic 自动化

增加：

- 数据异常主动发现。
- 自动创建和跟踪处理任务。
- 周期准备度检查。
- 结算异常解释。
- 制度健康度分析。
- 受控的自主权分级。

### 第四阶段：验证悬赏市场

只有在基础激励计算与结算稳定后，再决定悬赏市场的完整交付节奏。

如果悬赏本身就是首个客户的核心场景，也可以提前实施，但应单独定义范围、预算控制和验收标准，避免它拖累整个结算主链路。

# 六、需要增加的端到端验收场景

当前 PRD 已经列出了几项 P0 验收标准，包括制度配置化、双引擎差异为零、评价证据挂载率、未确认金额零生效、权限测试和 AI 关闭后的人工降级。

这些标准应当保留，但还需要补充真实业务场景。

我建议至少增加以下验收测试：

| 场景 | 验收要求 |
|---|---|
| 正常考核与结算 | 从数据采集到员工确认和结算导出全流程完成 |
| 数据缺失 | 不允许将未知值自动当作零 |
| 重复数据 | 重复事件不会重复生成事实或重复支付 |
| 回款延迟 | 数据未达到规定条件时，不错误确认提成 |
| 退款或坏账 | 按明确规则生成冲销或调整记录 |
| 考核中途改规则 | 历史周期仍遵循适用版本，除非批准了明确的追溯策略 |
| 员工提出异议 | 保留原结果，按流程复核，不绕过权限直接改金额 |
| 审批人利益冲突 | 系统阻止不符合回避规则的审批 |
| Agent 生成错误评价 | 评价不能绕过人工确认直接生效 |
| Agent 工具调用失败 | 可以恢复或转人工，不留下无法追踪的半完成状态 |
| 跨租户访问 | 通过自动化安全测试验证数据隔离 |
| 结算导出失败 | 可安全重试，不产生重复结算 |
| 数据更正 | 能识别受影响的评价和金额，并按规则启动复核或重算 |

此外，所有关键测试都应该能够在 CI 中自动执行，而不只是由测试人员在页面上手工操作。

**核心目标不是把 PRD 写得更长，而是让每一项核心需求都具备明确的业务语义、可执行的实现路径、可验证的验收条件，以及发生异常时的安全处理机制。**

# 二、重新定义核心业务闭环

我建议把系统的核心业务闭环明确为：

**业务事实产生 → 数据采集 → 证据验证 → 贡献归属 → 绩效评价 → 激励计算 → 人工审核 → 员工确认或申诉 → 正式结算 → 结果反馈 → 制度改进。**

这不是简单的线性工作流。实际业务中，数据更正、异议、退款和规则变化都可能使流程返回之前的环节。

因此，系统需要区分三个层次。

### 1. 事实层

负责回答：业务上实际发生了什么？

例如：
- 客户支付了一笔货款。
- 员工完成了一项任务。
- 某项交付物通过验收。
- 某订单发生退款。
- 某个项目产生了可确认的利润。

事实层不负责判断某个员工应该获得多少奖金。

### 2. 决策层

负责回答：根据当前制度和经过确认的事实，应该如何评价与计算？

包括：
- 指标计算。
- 贡献归属。
- 绩效评分。
- 激励资格判定。
- 奖金和提成计算。
- 预算约束。
- 异议与复核。

其中，AI 可以提出评价建议，但最终决策必须遵循相应的授权和审核规则。

### 3. 执行层

负责回答：经过批准的决策是否已经完成业务执行？

包括：
- 正式确认。
- 金额锁定。
- 结算文件生成。
- 财务对账。
- 发放状态回写。
- 异常追踪。
- 冲销与调整。

**必须避免把“AI 已生成结果”“管理者已确认”和“财务已完成结算”当作同一件事。**

它们具有不同的业务含义，也必须拥有不同的状态和权限。

# 三、建立统一的考核与结算状态机

V3.0 已经设计了 EvaluationCycle、EvaluationDraft、Confirmation 和 AmountLedger 等核心对象，但还需要明确它们之间的状态转换规则。

建议 V3.1 采用以下设计。

## 3.1 考核周期状态机

| 状态 | 含义 | 允许的操作 |
|---|---|---|
| DRAFT | 周期配置草稿 | 修改指标与规则配置 |
| COLLECTING | 收集业务数据 | 接收事件、同步数据 |
| DATA_REVIEW | 数据完整性检查 | 补充、核实和处理冲突 |
| EVALUATING | 生成评价草稿 | Agent 评价、人工初评 |
| MANAGER_REVIEW | 管理者审核 | 确认、修改或退回 |
| EMPLOYEE_REVIEW | 员工查看结果 | 确认、提出异议 |
| APPEAL_REVIEW | 异议复核 | 复核证据与评价 |
| READY_TO_SETTLE | 满足结算前置条件 | 生成最终激励试算 |
| SETTLING | 正式结算处理中 | 对账、导出、回写 |
| CLOSED | 周期关闭 | 查看历史结果、按授权发起调整 |

这些状态并不意味着所有企业都必须使用完全相同的流程。

制度无关架构应该允许租户配置适用的流程、审批人和部分可选环节，同时保留系统级安全约束。

例如，企业可以配置不同的绩效审核流程，但不能通过配置关闭跨租户隔离，或者让未经授权的 Agent 直接修改金额账本。

### 必须补充的状态转换规则

每一次状态转换都应记录：

- 原状态与目标状态。
- 操作主体。
- 触发原因。
- 必要的前置条件。
- 关联的规则版本与证据快照。
- 操作时间。
- 成功或失败结果。

同时必须支持幂等执行。

例如，同一条飞书 webhook 被重复发送三次，不能让考核周期重复推进，也不能导致同一笔奖金被计算或导出三次。

## 3.2 激励计算与金额账本状态机

建议将激励计算与考核周期分开。

| 状态 | 含义 |
|---|---|
| NOT_CALCULATED | 尚未计算 |
| CALCULATING | 正在计算 |
| CALCULATED | 计算完成 |
| BLOCKED | 存在阻断问题 |
| NEEDS_REVIEW | 需要人工判断 |
| RECONCILIATION_REQUIRED | 独立对照或财务对账尚未通过 |
| PENDING_APPROVAL | 等待授权人员批准 |
| APPROVED | 已批准 |
| LOCKED | 金额账本已锁定 |
| ADJUSTMENT_REQUIRED | 后续事实变化，需评估是否调整 |
| REVERSED | 已按规则冲销 |

这里有两个重要原则。

**第一，计算成功不代表可以结算。**

如果数据不完整、规则版本不明确，或者独立对照结果不一致，即使主引擎已经算出一个数字，也不能把它作为正式应付金额。

**第二，金额账本锁定不代表历史事实永远不能变化。**

例如，某订单在季度结束后发生退款。

系统应保留原始结算记录，再根据已批准的业务规则生成调整或冲销记录，而不是直接覆盖历史金额。

这样才能同时满足财务追溯和历史重现要求。

## 3.3 申诉不能直接修改原始结果

建议将申诉设计成独立业务对象。

完整流程为：

员工提出异议 → 系统创建申诉案件 → 收集相关证据 → 指派独立复核人 → 形成复核结论 → 必要时重新评价 → 必要时重新计算 → 记录调整原因。

复核人员不能是原决定的唯一复核者，也不能因为申诉成立就直接修改金额字段。

如果复核改变了绩效结果，系统应明确记录：

1. 原始结果。
2. 原始证据与规则版本。
3. 复核新增或修正的事实。
4. 新的评价结论。
5. 重新计算后的金额。
6. 相关审批记录。

这也是后续建立自动化回归测试的重要基础。

# 四、规则引擎必须从“公式集合”升级为“可审计的业务规则系统”

V3.0 已经提出声明式 DSL、固定原语、规则版本化、定点小数和独立对照。

我建议 V3.1 进一步规定，每条规则必须具备以下结构：

| 属性 | 要求 |
|---|---|
| Rule ID | 全局唯一标识 |
| Rule Version | 不可变版本号 |
| Applicable Scope | 适用租户、人员范围、周期和激励类型 |
| Effective Period | 生效时间及适用周期 |
| Inputs | 输入字段、来源、单位和完整性要求 |
| Preconditions | 计算前置条件 |
| Formula | 确定性的计算表达式 |
| Rounding | 精度与舍入规则 |
| Missing Data Policy | 缺失数据的处理方式 |
| Conflict Policy | 与其他规则冲突时的处理方式 |
| Approval Record | 批准人、批准时间和变更依据 |
| Test Cases | 标准、边界和异常测试案例 |

规则应当是不可变版本。

需要修改规则时，创建新版本，并明确其生效范围。

如果确实需要追溯调整历史周期，应走单独的授权流程，保留原始计算结果，并记录追溯调整的理由和影响范围。

## 4.1 统一缺失数据处理

建议将输入数据状态标准化为：

- `VALID`：数据有效且满足计算条件。
- `MISSING`：数据缺失。
- `STALE`：数据超过允许的时效。
- `CONFLICTED`：多个来源存在未解决冲突。
- `UNVERIFIED`：数据尚未达到所需的确认等级。
- `INVALID`：数据不符合字段约束或业务规则。

规则引擎必须根据每项输入的状态决定是否继续计算。

不能把所有异常都统一处理成零，也不能让 Agent 自行猜测缺失值。

## 4.2 统一计算结果解释

每次计算都应生成可审计的结果明细。

例如：

| 项目 | 示例 |
|---|---|
| 激励类型 | 销售提成 |
| 输入业务对象 | 订单 A |
| 计提基数 | 经过确认的回款金额 |
| 适用规则 | COMMISSION-RULE-V3 |
| 资格判断 | 满足计提条件 |
| 计算过程 | 按规则逐步执行 |
| 舍入规则 | 使用租户批准的精度与舍入方式 |
| 最终结果 | 确定性计算金额 |
| 输入快照 | 对应的不可变快照 |
| 计算状态 | 已完成或阻断 |

这里的金额仅是结构示例，不代表 Anari 已经批准的具体业务公式。

另外，系统应允许财务和授权管理者查看计算依据，但不能让普通员工因此获得其他员工的敏感信息。

# 五、V3.1 的第一轮验收标准

建议将以下要求加入开发验收清单。

### 规则引擎

- 同一输入快照、同一规则版本和同一执行语义下，重复计算结果一致。
- 每条正式规则都有经过业务确认的测试案例。
- 规则变更后可以进行历史回放与差异比较。
- 缺失、冲突或未验证的数据不会被静默转换成零。
- 未通过必要校验的金额不能进入正式结算。

### 工作流

- 每种状态都有明确的进入条件和允许操作。
- 未授权角色不能推进关键状态。
- 重复事件和重复请求不会造成重复处理。
- 失败的异步任务能够重试、恢复或转人工。
- 已锁定的历史账本不能被普通更新操作覆盖。

### 评价与申诉

- 评价观点可以定位到实际证据。
- 证据不足时允许系统拒绝作出确定性判断。
- 员工异议不会直接覆盖原评价。
- 复核与原始决定之间具备独立性约束。
- 评价修正对金额的影响可以被完整追溯。

### 结算

- 计算、审批、锁定、导出和财务回写是可区分的步骤。
- 导出失败后可以安全重试。
- 退款、坏账及数据更正能够进入明确的调整流程。
- 每笔正式结算都可以追溯到适用规则版本和输入快照。

# 一、证据图谱：从记录业务事实升级为支撑决策的证据系统

## 1.1 先明确一个核心问题

假设 Anari 的一个海外客户订单最终实现了回款。

这个结果可能涉及销售、技术支持、产品经理、供应链和管理人员。

系统可以从 CRM、ERP、任务管理系统等来源获得相关记录，但这些记录不能直接回答：

- 谁对订单结果作出了实际贡献？
- 每个人的贡献是什么？
- 贡献是独立完成，还是团队协作完成？
- 相关成果是否已经验收？
- 订单回款是否可以计入当前考核周期？
- 该成果是否已经在其他激励项目中获得奖励？

因此，必须区分三个不同的概念：

**事实真实、贡献成立、激励符合规则。**

它们是三个不同的判断，不能由一个 AI Agent 一次性完成。

## 1.2 建议采用五层证据模型

在 V3.0 的 `EvidenceNode` 基础上，增加明确的证据分类和关系模型。

| 层次 | 核心对象 | 作用 | 示例 |
|---|---|---|---|
| L1 原始事实 | RawEvent | 保存从业务系统获取的原始事件 | CRM 订单更新、ERP 回款记录 |
| L2 标准化事实 | EvidenceNode | 将不同来源的数据转换为统一业务语义 | 已确认回款金额 |
| L3 贡献申报 | ContributionClaim | 记录员工或系统提出的贡献主张 | 技术支持人员申报完成客户技术方案 |
| L4 贡献认定 | AttributionDecision | 记录经授权确认的贡献归属 | 确认某员工完成了指定交付任务 |
| L5 决策结果 | EvaluationDecision / AmountLedger | 形成正式评价与激励结果 | 已确认绩效、已批准提成 |

这里有一项重要的设计原则：

**L1 到 L2 的数据标准化，不应自动产生 L4 的贡献认定。**

例如，系统发现某员工在一份技术方案文档中留下了编辑记录，可以将其作为参与证据，但不能仅凭编辑记录就认定该员工承担了方案的主要工作。

同样，订单已经回款，也不代表相关员工自动取得提成资格。是否计提，应由适用的激励规则决定。

### 原 PRD 中哪些内容需要保留？

V3.0 已经规定了证据来源、事件 ID、主体、对象、置信度、完整度和时间戳等字段。

这些字段可以继续保留。

建议在其基础上补充：

- `source_system`：来源系统。
- `source_record_id`：来源记录的唯一标识。
- `source_event_id`：来源事件的唯一标识。
- `event_time`：业务事件实际发生时间。
- `observed_at`：本系统观察到事件的时间。
- `normalized_at`：标准化处理时间。
- `verification_status`：验证状态。
- `correction_of`：被更正的原始记录。
- `superseded_by`：替代该记录的新版本。
- `evidence_schema_version`：证据结构版本。

这里必须区分业务发生时间与系统采集时间。

例如，一笔回款发生在 9 月 30 日，但 ERP 数据在 10 月 2 日才同步到绩效系统。系统应保留两个时间，避免因为数据延迟而错误地把业务事实归入 10 月。

至于这笔回款最终属于哪个考核周期，则应由经过批准的周期归属规则决定。

## 1.3 证据不能只有置信度，还必须有验证状态

V3.0 已经考虑了证据置信度，但置信度本身并不足以决定一项事实是否可以用于正式结算。

例如，AI 对一条订单记录的识别置信度达到 99%，也不代表订单金额已经与财务系统核对。

建议将以下维度分开建模：

| 维度 | 示例 |
|---|---|
| 来源可靠性 | 来自 ERP 正式记录，还是员工手工填写 |
| 数据完整性 | 是否包含必要字段 |
| 数据验证状态 | 已验证、待验证、存在冲突 |
| 语义匹配置信度 | AI 是否正确识别了记录含义 |
| 业务确认状态 | 是否经过有权限的人员确认 |
| 使用限制 | 可用于分析、评价参考或正式计算 |

特别注意：

**置信度是对不确定性的估计，不是业务授权。**

因此，正式计算规则应该明确规定允许使用哪些验证状态的证据，而不是简单地设定一个统一置信度阈值。

# 二、贡献归属：不能让 AI 直接决定员工应得多少

这是整个系统最容易出现争议的部分之一。

## 2.1 将贡献申报与贡献认定分开

建议新增两个核心对象。

### ContributionClaim：贡献申报

记录某个主体对一项工作或成果提出的贡献主张。

至少包含：

| 字段 | 说明 |
|---|---|
| claim_id | 申报唯一标识 |
| tenant_id | 所属租户 |
| claimant_id | 申报人 |
| contribution_type | 贡献类型 |
| related_object_ids | 关联任务、项目、订单或成果 |
| evidence_refs | 支撑该主张的证据 |
| claimed_scope | 申报的工作范围 |
| claimed_period | 申报的贡献时间范围 |
| status | 草稿、待审核、已确认、驳回或撤回 |
| submitted_at | 提交时间 |

员工可以通过表单、对话或自动生成的申报草稿提交材料。

AI 可以帮助整理描述、关联任务和发现遗漏，但不能未经员工确认，就把 AI 推断的贡献直接登记为员工已经认可的申报。

### AttributionDecision：贡献认定

记录经过授权的贡献归属结果。

至少包含：

- 关联的贡献申报。
- 关联的业务事实与交付物。
- 认定主体及认定依据。
- 适用的贡献归属规则。
- 认定结果与理由。
- 审批人及审批时间。
- 版本号。
- 后续更正或撤销记录。

需要特别说明：不是所有贡献都必须经过独立人工审批。

企业可以根据贡献类型、风险等级和制度规定，配置不同的确认流程。

例如，简单的任务完成事实可以由系统根据经过验证的任务状态自动确认；涉及团队贡献分配或较大金额激励的归属，则可以要求管理者审核。

**权限和确认强度应由业务风险决定，而不是一律人工处理或一律交给 AI。**

## 2.2 贡献认定不等于奖金分配

假设一个项目的交付涉及三个人。

系统可以记录：

- 员工 A：完成技术方案。
- 员工 B：负责客户协调。
- 员工 C：完成现场部署。

这些记录可以作为贡献事实。

但接下来如何评价贡献、是否获得专项奖励，以及奖金如何分配，仍然属于不同的业务决策。

不要在证据图谱里直接写入一个由 AI 估算的奖金金额。

如果制度规定某类项目按贡献比例分配奖金，那么应由对应的正式规则执行，并记录每个参与者的分配依据。

如果制度没有规定如何分配，系统应该提示规则缺失，而不是让模型临时决定比例。

## 2.3 防止重复计奖

V3.0 已经通过悬赏契约、激励记录和抵扣规则考虑了重复计奖与冲销问题。

建议进一步为每笔激励记录建立统一的计奖依据。

可以使用如下逻辑关系：

`IncentiveRecord → AttributionDecision → EvidenceNode`

也就是说，每笔激励都应能够回答：

1. 奖励针对什么业务成果？
2. 奖励归属于谁？
3. 依据哪些经过验证的事实？
4. 适用哪一项制度规则？
5. 是否与其他激励存在冲突？

同时，不能把“关联同一个订单”简单等同于“重复计奖”。

例如，销售提成可能奖励销售结果，技术专项奖金可能奖励额外交付成果。即使两者来自同一个订单，也可能符合制度。

真正需要判断的是：奖励对象、贡献范围、计奖条件和制度约束是否重叠。

建议采用两级机制：

- **确定性冲突检测**：根据规则 ID、成果标识、激励类型和适用范围判断明确禁止的重复计奖。
- **语义风险检测**：由 AI 识别可能存在的成果重叠，生成待复核事项。

第二种机制不应仅凭语义相似度就直接冻结或扣除奖金。

# 三、数据更正与历史追溯：建立真正的证据血缘

证据图谱如果不能处理历史更正，就无法支撑长期运行的绩效和激励系统。

例如：

9 月的一笔订单回款已经计入第三季度提成，10 月才发现原始回款金额存在错误。

系统不能简单覆盖原始数据，然后让历史账本看起来像从未发生过错误。

建议采用追加式更正机制。

## 3.1 更正流程

1. 接收到原始数据更正事件。
2. 验证事件来源和权限。
3. 创建更正记录，并关联原始证据。
4. 标记受影响的标准化事实。
5. 根据证据关系找到受影响的贡献认定、评价和激励记录。
6. 评估是否需要重新评价或重新计算。
7. 按制度要求发起审批。
8. 生成调整、冲销或补发记录。
9. 保存完整的前后版本与操作审计。

这里不应要求所有更正都自动重算整家公司全部绩效。

系统应通过依赖关系识别受影响的对象，并根据影响范围决定处理方式。

例如，某个订单的回款金额发生变化，可能只影响与该订单相关的提成，而不必重新计算完全无关的培训成绩。

## 3.2 建议新增的数据对象

| 对象 | 目的 |
|---|---|
| EvidenceCorrection | 记录事实更正与原始记录的关系 |
| EvidenceDependency | 记录证据被哪些决策使用 |
| RecalculationRequest | 记录重算请求及触发原因 |
| AdjustmentRecord | 记录正式的补发、冲销或扣回 |
| ImpactAssessment | 评估更正对绩效和激励结果的影响 |

这些对象不一定都必须实现为独立数据表，但必须在架构和接口层明确其职责。

### 验收要求

对任意一笔正式激励记录，系统都应能追溯到：

- 原始业务事实。
- 标准化后的证据。
- 经过确认的贡献归属。
- 适用的绩效评价。
- 规则版本。
- 输入快照。
- 审批记录。
- 后续更正及调整。

如果其中某个环节缺失，系统应明确显示缺失或异常，而不是生成一条看似完整的解释。

# 四、Agentic 执行架构：从生成建议升级为完成任务

接下来是本轮最重要的部分。

V3.0 已经提出 Evaluation Agent、Insight Agent、申报辅助和悬赏匹配，并明确要求 Agent 不得直接修改正式金额。

这些边界应当继续保留。

但如果要真正实现 Agentic 能力，还需要一层统一的执行框架。

## 4.1 建议增加 Agent Runtime

Agent Runtime 不是一个新的聊天机器人，而是所有 Agent 执行任务时共用的控制层。

建议职责包括：

- 接收定时任务、业务事件和人工请求。
- 判断是否需要启动 Agent。
- 创建有明确目标的执行任务。
- 向 Agent 提供经过授权的数据上下文。
- 限制可调用的工具。
- 记录每次工具调用及执行结果。
- 检查是否需要人工审批。
- 跟踪任务状态。
- 处理超时、重试和失败恢复。
- 在完成后验证业务结果。

建议执行流程为：

**事件触发 → 任务创建 → 权限检查 → 上下文构建 → Agent 规划 → 工具调用 → 结果验证 → 审批或继续执行 → 任务关闭 → 审计记录。**

这里有一个重要区别：

Agent 的自然语言回复不等于任务完成。

例如，Agent 说“已完成绩效数据核对”，并不能证明数据确实已经核对。

只有当对应的核对任务、验证结果和必要的审计记录都已成功提交，工作流才能将任务标记为完成。

## 4.2 统一 Agent 任务对象

建议新增 `AgentTask`。

| 字段 | 说明 |
|---|---|
| task_id | 唯一任务标识 |
| tenant_id | 租户标识 |
| trigger_type | 定时、事件、人工请求等 |
| task_type | 数据核查、评价准备、异常处理等 |
| target_object | 目标业务对象 |
| objective | 明确的执行目标 |
| input_snapshot | 任务启动时使用的输入快照 |
| permission_scope | 可读取和操作的对象范围 |
| autonomy_level | 当前任务允许的自主权等级 |
| status | 当前执行状态 |
| attempt_count | 已尝试次数 |
| deadline | 任务期限 |
| approval_required | 是否需要审批 |
| result | 结构化执行结果 |
| failure_reason | 失败原因 |
| created_at / updated_at | 生命周期时间 |

不建议把全部中间推理内容都存入业务数据库。

应重点保存任务目标、输入依据、工具调用、关键决策、验证结果和执行状态，以满足审计、调试和故障恢复需求。

## 4.3 建立 Agent 任务状态机

建议至少支持：

`QUEUED → RUNNING → WAITING_APPROVAL → RUNNING → SUCCEEDED`

同时支持：

- `RETRY_PENDING`：等待重试。
- `BLOCKED`：存在尚未解决的阻断条件。
- `FAILED`：执行失败。
- `CANCELLED`：任务已取消。
- `ESCALATED`：已升级给人工处理。

并非所有任务都需要经过审批，也并非所有失败都应该自动重试。

例如：

| 任务 | 建议行为 |
|---|---|
| 生成评价草稿 | 可以自动执行，结果仍需审核 |
| 检查缺失数据 | 可以自动执行并生成问题清单 |
| 创建普通提醒 | 经授权后可以自动执行 |
| 修改正式绩效结果 | 必须经过相应确认 |
| 修改奖金规则 | 必须走正式规则变更流程 |
| 批准正式结算 | 不得因 Agent 自主权升级而自动获得权限 |

**Agent 的权限应该绑定具体动作，而不是仅绑定一个 L0、L1 或 L2 标签。**

# 五、主动工作流：系统如何自己发现问题并推动解决

我建议把 Agentic 能力的第一个真实落点放在“考核准备度与异常处理”上，而不是先做复杂的全自动绩效决策。

原因很简单：数据缺失、事实冲突和流程逾期是明确可识别的问题，也比较容易衡量自动化是否真的创造了价值。

## 5.1 场景：季度考核准备度检查

系统在考核周期结束前自动执行：

1. 检查必要数据源是否正常同步。
2. 检查关键指标是否存在缺失或过期数据。
3. 检查订单、任务和回款记录之间是否存在冲突。
4. 检查贡献申报是否已经完成必要确认。
5. 检查评价所需的证据是否充分。
6. 检查待审批事项是否逾期。
7. 生成考核准备度报告。
8. 为每个问题创建相应的处理任务。
9. 指派有权限的责任人。
10. 跟踪处理进度。
11. 在数据修正后重新验证。
12. 只有所有强制性阻断项满足条件后，才允许进入下一阶段。

这就形成了一个完整的业务闭环。

但需要注意：准备度达到 100% 只能说明所有规定的检查项均已满足，不能保证评价本身绝对正确。

## 5.2 建立统一的 DataQualityIssue

建议为数据问题建立统一对象。

主要字段包括：

- `issue_id`
- `tenant_id`
- `issue_type`
- `severity`
- `related_object_ids`
- `description`
- `evidence_refs`
- `owner_id`
- `due_at`
- `status`
- `resolution`
- `verified_at`

建议的严重级别：

| 级别 | 示例 | 处理策略 |
|---|---|---|
| INFO | 非关键字段缺失 | 提示 |
| WARNING | 数据延迟但尚未影响计算 | 追踪 |
| ERROR | 指标数据冲突 | 必须处理或按批准规则排除 |
| BLOCKER | 关键计提数据无法验证 | 阻止正式结算 |

这里的等级应允许租户配置，但系统必须保留最低安全约束。

例如，如果正式结算必须依赖实际回款，而当前回款数据存在未解决冲突，那么不能通过降低问题严重等级来绕过结算校验。

# 六、Agent 工具权限：把安全边界落实到代码

这是 Agentic 系统必须具备的基础设施。

不能仅仅在系统提示词中写一句“不要修改金额”，就认为已经实现了安全隔离。

建议将工具分为四类。

| 工具类别 | 典型操作 | 默认策略 |
|---|---|---|
| 查询工具 | 查询权限内的证据、评价和状态 | 经授权后可自动调用 |
| 分析工具 | 检查数据完整性、计算准备度、识别异常 | 可以自动执行 |
| 业务写入工具 | 创建任务、提交草稿、发送提醒 | 根据动作风险配置 |
| 高风险工具 | 确认评价、批准金额、修改正式规则 | 独立权限与审批控制 |

其中，正式金额计算应由确定性规则引擎执行，而不是让 LLM 调用一个允许任意写入金额的通用数据库工具。

建议采用以下强制约束：

1. Agent 只能通过明确登记的工具访问业务系统。
2. 每次工具调用都执行租户、用户和对象级权限检查。
3. 工具服务端验证参数，不依赖 LLM 自觉遵守数据约束。
4. 重要写入操作必须具有幂等键。
5. 高风险操作必须验证审批记录与操作授权。
6. 工具调用的输入、输出摘要和执行结果进入审计链。
7. Agent 不能通过自由 SQL、任意脚本执行或通用数据库写入绕过业务服务层。
8. 任何自主权升级都不能突破系统级权限限制。

对于多 Agent 协作，建议每个 Agent 使用独立的任务上下文和最小权限集合。一个 Agent 的输出可以成为另一个 Agent 的输入，但不能因此自动继承对方的全部权限。

# 七、失败恢复与人工接管

真实生产系统一定会遇到失败。

可能是飞书 API 限流、CRM 暂时不可用、模型调用超时，也可能是审批人长期未处理任务。

如果系统只设计成功路径，就不具备生产可用性。

## 7.1 重试策略

建议区分三种失败：

**可恢复失败**

例如网络超时、临时服务不可用。

可以采用带退避策略的有限次数重试。

**业务阻断**

例如缺少关键回款数据、规则未配置、贡献归属存在争议。

不应该不断重试，而应创建问题并等待人工处理或新的业务事件。

**不可恢复失败**

例如参数违反业务约束、权限不足、规则版本无效。

应立即停止相关执行，并记录失败原因。

## 7.2 幂等控制

所有会产生业务副作用的工具，都应定义幂等策略。

例如：

- 创建同一条异常任务不能重复生成多个待办。
- 重复接收同一笔回款事件不能重复入账。
- 同一结算批次的重复导出不能造成重复支付。
- 重复提交审批请求不能让审批流程进入不一致状态。

对于涉及外部系统的操作，不能仅依赖数据库事务。

还需要通过幂等键、操作记录、外部系统回执和定期对账，处理网络中断后无法确定操作是否成功的情况。

## 7.3 人工接管

当任务满足以下任一条件时，建议转入人工处理：

- 超过最大重试次数。
- 关键数据存在无法自动解决的冲突。
- 超过处理期限。
- 所需操作超出 Agent 权限。
- 发现潜在重复计奖。
- 评价证据不足。
- 规则存在歧义。
- 发现可能影响正式结算的异常。

人工接管不是系统失败，而是受控自动化的一部分。

系统应保留已完成的工作、未解决的问题、已有证据和建议的下一步，避免人工接手后重新从头排查。

> ## 1.3 关键业务不变量
> 
> 以下规则应成为服务端校验和自动化测试的一部分：
> 
> 1. 未通过必要数据质量检查的记录，不得进入正式计算。
> 2. AI 评价草稿不能直接替代正式评价决定。
> 3. 未经批准的规则版本不能用于正式结算。
> 4. 同一业务事件重复到达，不得重复产生激励。
> 5. 已锁定的正式金额记录不得被普通更新覆盖。
> 6. 历史更正必须保留原始记录及更正关系。
> 7. 申诉不能直接删除或覆盖原始评价。
> 8. Agent 不得通过通用数据库写入绕过业务规则。
> 9. 所有高风险操作必须具备服务端授权校验。
> 10. 关闭 AI 服务后，必要的人工业务流程仍应可运行。
> 
> 这些不变量必须通过自动化测试验证，而不能只写在开发规范或系统提示词中。
>

> # 第二部分：端到端测试矩阵
> 
> ## 2.1 正常业务路径
> 
> | 编号 | 场景 | 预期结果 | 优先级 |
> |---|---|---|---|
> | E2E-001 | 数据源正常同步 | 生成标准化证据，保留来源信息 | P0 |
> | E2E-002 | 员工提交贡献申报 | 形成申报记录，关联对应证据 | P0 |
> | E2E-003 | 管理者确认贡献归属 | 生成有版本和审计记录的认定结果 | P0 |
> | E2E-004 | AI 生成绩效评价草稿 | 输出评分建议、依据和缺口 | P0 |
> | E2E-005 | 管理者确认评价 | 形成正式评价决定和确认记录 | P0 |
> | E2E-006 | 规则引擎执行激励计算 | 生成可复现的计算结果及输入快照 | P0 |
> | E2E-007 | 结算审批通过 | 生成已批准的结算批次 | P0 |
> | E2E-008 | 结算结果导出 | 导出结果与账本一致，可追溯 | P0 |
> 
> **完成定义：** 每个场景必须从实际入口执行到最终结果，不能只测试单个函数或孤立 API。
> 
> ## 2.2 数据质量与异常处理
> 
> | 编号 | 场景 | 预期结果 | 优先级 |
> |---|---|---|---|
> | E2E-101 | 关键指标缺失 | 创建问题，阻止不满足条件的计算 | P0 |
> | E2E-102 | 同一事件重复同步 | 识别重复事件，不重复入账 | P0 |
> | E2E-103 | 不同来源的数据冲突 | 标记冲突并进入复核流程 | P0 |
> | E2E-104 | 数据晚于考核周期到达 | 保留业务时间与采集时间，按已批准规则处理 | P0 |
> | E2E-105 | 原始数据被更正 | 形成更正记录，识别受影响的下游对象 | P0 |
> | E2E-106 | 数据源暂时不可用 | 记录同步失败，允许安全恢复 | P0 |
> | E2E-107 | 数据格式错误 | 拒绝或隔离异常数据，不静默转零 | P0 |
> | E2E-108 | 数据恢复后重新同步 | 不重复产生业务副作用 | P0 |
> 
> 对缺失数据的处理不能统一规定为“阻止所有计算”。
> 
> 具体策略应由规则配置决定：有些指标可以延期或排除，有些指标必须阻止结算。系统不得擅自猜测缺失值。
> 
> ## 2.3 规则引擎与金额正确性
> 
> | 编号 | 场景 | 预期结果 | 优先级 |
> |---|---|---|---|
> | CALC-001 | 相同输入与相同规则版本重复计算 | 结果完全一致 | P0 |
> | CALC-002 | 阶梯边界值 | 严格符合规则定义 | P0 |
> | CALC-003 | 舍入与精度处理 | 符合已批准的精度规则 | P0 |
> | CALC-004 | 输入快照发生变化 | 形成新计算运行记录，不覆盖旧结果 | P0 |
> | CALC-005 | 规则版本发生变化 | 历史结果仍绑定原规则版本 | P0 |
> | CALC-006 | 退款或坏账发生 | 按已批准规则生成调整或冲销记录 | P0 |
> | CALC-007 | 计算结果与独立对照实现不一致 | 阻断正式结算并报告差异 | P0 |
> | CALC-008 | 未批准规则被请求使用 | 拒绝正式计算 | P0 |
> | CALC-009 | 重复提交结算请求 | 不重复生成支付或结算副作用 | P0 |
> | CALC-010 | 负数、超限或无效输入 | 根据规则校验，不能静默接受异常结果 | P0 |
> 
> 独立对照实现应尽可能采用不同的计算路径，避免两个实现共享同一个错误。
> 
> 测试应覆盖正常值、边界值、异常值和随机生成的输入。
> 
> 如果规则引擎存在差异，系统必须记录差异并阻断相关结算，而不是选择其中一个结果继续执行。
> 
> ## 2.4 评价与申诉
> 
> | 编号 | 场景 | 预期结果 | 优先级 |
> |---|---|---|---|
> | EVA-001 | 有充分证据 | AI 生成带依据的评价草稿 | P0 |
> | EVA-002 | 证据不足 | 明确标记缺口，不伪造依据 | P0 |
> | EVA-003 | 证据相互矛盾 | 提示冲突，按规则进入复核 | P0 |
> | EVA-004 | 管理者修改 AI 评价 | 保留原草稿和修改记录 | P0 |
> | EVA-005 | 员工提出申诉 | 建立独立申诉案件 | P0 |
> | EVA-006 | 申诉改变评价结果 | 形成新决策版本，保留原结果 | P0 |
> | EVA-007 | 申诉不改变结果 | 记录复核依据和结论 | P0 |
> | EVA-008 | 评价人员同时是申诉相关决策人 | 按利益冲突策略限制或升级处理 | P0 |
> | EVA-009 | AI 服务不可用 | 允许使用人工评价流程 | P0 |
> 
> 评价质量不能只用 AI 建议的采纳率衡量。
> 
> 应至少监控：
> 
> - 与经过校准的人工评价之间的差异。
> - 评价被修改的比例及修改幅度。
> - 证据不足时的正确拒答率。
> - 不同员工群体之间的异常差异。
> - 申诉率及申诉改判率。
> - 不同模型版本的评价质量变化。
> 
> 指标阈值应根据首批真实业务数据建立基线，再由产品与业务负责人批准，不应凭空设置一个通用数字。
> 
> ## 2.5 Agent 执行与恢复
> 
> | 编号 | 场景 | 预期结果 | 优先级 |
> |---|---|---|---|
> | AGT-001 | 定时任务启动 | 创建唯一任务实例 | P0 |
> | AGT-002 | 同一事件重复触发 | 不重复创建具有相同业务效果的任务 | P0 |
> | AGT-003 | 工具调用超时 | 按策略重试或转入人工处理 | P0 |
> | AGT-004 | 工具执行成功但响应丢失 | 通过幂等记录或对账识别执行状态 | P0 |
> | AGT-005 | Agent 请求越权操作 | 服务端拒绝并记录审计事件 | P0 |
> | AGT-006 | 需要人工审批 | 进入待审批状态，不能提前执行高风险动作 | P0 |
> | AGT-007 | 人工拒绝审批 | 终止或调整工作流，不绕过拒绝结果 | P0 |
> | AGT-008 | 任务超时 | 标记超时并执行升级策略 | P0 |
> | AGT-009 | Agent 服务关闭 | 核心人工流程仍可运行 | P0 |
> | AGT-010 | 模型升级 | 可对照评估，不自动改变正式业务规则 | P0 |
> 
> **Agent 的成功率必须按业务结果衡量，而不是按模型是否返回 HTTP 200 或是否生成一段完整文字衡量。**
> 
> ## 2.6 多租户与权限测试
> 
> | 编号 | 场景 | 预期结果 | 优先级 |
> |---|---|---|---|
> | SEC-001 | 租户 A 查询租户 B 的记录 | 服务端拒绝访问 | P0 |
> | SEC-002 | 员工查询无权查看的同事评价 | 拒绝访问或按批准策略脱敏 | P0 |
> | SEC-003 | Agent 跨租户读取证据 | 拒绝访问 | P0 |
> | SEC-004 | 通过导出接口绕过页面权限 | 服务端仍然拒绝未授权导出 | P0 |
> | SEC-005 | 异步任务使用过期或错误权限上下文 | 拒绝执行或重新授权 | P0 |
> | SEC-006 | 缓存命中其他租户数据 | 不得泄露跨租户信息 | P0 |
> | SEC-007 | 未授权用户修改规则 | 拒绝并保留审计记录 | P0 |
> | SEC-008 | 普通 Agent 试图修改金额账本 | 拒绝写入 | P0 |
> 
> 必须测试页面、API、异步任务、缓存、搜索、文件导出及 Agent 工具等全部数据访问路径。
>

> # 第三部分：安全、权限与合规验收
> 
> ## 3.1 多租户隔离
> 
> 每个业务对象必须明确归属租户。
> 
> 租户隔离不能只依赖前端过滤或开发者记得添加 `tenant_id` 条件。
> 
> 实施时应根据所选数据库与部署架构，采用适当的服务端访问控制、数据库约束、行级安全或独立 schema 等措施。
> 
> 必须验证：
> 
> - 读取隔离。
> - 写入隔离。
> - 异步任务隔离。
> - 缓存隔离。
> - 搜索与向量检索隔离。
> - 文件及导出隔离。
> - 日志与错误信息隔离。
> 
> 具体采用行级隔离还是独立 schema，应根据租户规模、监管要求、运维能力和成本做正式架构决策。
> 
> ## 3.2 权限模型
> 
> 建议至少包含以下角色类别：
> 
> - 租户管理员。
> - 制度管理员。
> - 人力资源或绩效管理人员。
> - 部门管理者。
> - 普通员工。
> - 财务审核人员。
> - 审计人员。
> - 系统运维人员。
> - Agent 服务身份。
> 
> 角色只用于描述基础职责，最终授权还必须考虑对象归属、操作类型和业务状态。
> 
> 例如，部门管理者可以查看自己管理范围内的评价草稿，并不意味着其自动拥有批准所有员工奖金或修改激励规则的权限。
> 
> 关键权限应实行服务端校验，并对规则变更、正式结算及其他高风险操作实施适当的职责分离。
> 
> ## 3.3 绩效数据的隐私保护
> 
> 绩效评价、工作行为记录和薪酬激励数据可能属于敏感的人事数据。
> 
> 建议在产品层面提供：
> 
> 1. 清晰的数据使用目的。
> 2. 数据来源与处理记录。
> 3. 按角色和业务目的控制访问。
> 4. 数据导出和共享控制。
> 5. 适用的数据保留及删除机制。
> 6. 员工查看自身相关信息的适当渠道。
> 7. 评价更正与申诉流程。
> 8. AI 参与评价的透明度机制。
> 9. 模型调用的敏感字段最小化。
> 10. 数据泄露和安全事件处理流程。
> 
> 具体法定义务必须结合租户所在地、员工所在地、数据类型和实际业务模式核验。
> 
> 不能仅凭系统提供了告知书，就认定已经满足全部法律要求。
> 
> ## 3.4 LLM 数据保护
> 
> 建议建立模型调用数据白名单。
> 
> 在向外部模型发送数据前，系统应根据任务需要决定：
> 
> - 是否必须调用模型。
> - 是否可以使用本地模型。
> - 是否可以使用脱敏后的数据。
> - 哪些字段必须删除。
> - 是否允许发送评价内容或薪酬信息。
> - 模型供应商的处理与留存条件是否满足要求。
> 
> 模型输出应被视为不可信输入，必须经过结构校验、权限校验和业务规则校验。
> 
> 模型不能自行扩大其数据访问范围，也不能通过提示词中的指令改变工具权限。
> 
> ## 3.5 审计要求
> 
> 关键业务操作应记录：
> 
> - 操作主体。
> - 所属租户。
> - 操作类型。
> - 目标对象。
> - 操作时间。
> - 关联请求或任务 ID。
> - 变更前后版本或摘要。
> - 使用的规则或模型版本。
> - 审批依据。
> - 执行结果。
> 
> 审计记录应采用追加式设计，并限制普通业务角色修改或删除。
> 
> 审计系统本身也必须进行访问控制和完整性保护。
> 
> 日志不得无必要地记录完整敏感提示词、凭证或员工隐私数据。
>

> # 第四部分：性能与可靠性验收
> 
> V3.0 尚未提供足够明确的实际数据量和性能基线，因此不应直接虚构一个适用于所有租户的统一 SLA。
> 
> 建议先建立基准测试，再批准正式目标。
> 
> ## 4.1 必须测量的指标
> 
> | 指标类别 | 必须测量的内容 |
> |---|---|
> | 页面体验 | 核心页面响应时间、失败率 |
> | API | 延迟分布、错误率、超时率 |
> | 数据同步 | 延迟、失败率、重复事件率 |
> | 规则引擎 | 单次计算时间、批量计算吞吐量 |
> | Agent | 任务成功率、平均执行时间、重试率 |
> | 数据库 | 慢查询、锁等待、连接池使用率 |
> | 结算 | 批次完成时间、失败恢复时间 |
> | 成本 | 每个周期、每名员工及每次评价的模型成本 |
> | 稳定性 | 服务可用性、任务积压、故障恢复时间 |
> 
> ## 4.2 测试数据规模
> 
> 至少设计三档测试：
> 
> - **基础规模：** 首个租户的真实预期数据量。
> - **增长规模：** 预计未来一段时间内的业务增长量。
> - **压力规模：** 超出预期负载的测试，用于识别系统极限和退化方式。
> 
> 测试数据应覆盖员工、考核周期、证据、贡献申报、规则、激励记录、申诉和审计事件等关键对象。
> 
> 不应只用几条样例数据测试系统性能。
> 
> ## 4.3 故障恢复
> 
> 至少测试：
> 
> - 数据库连接中断。
> - 模型服务不可用。
> - 外部业务系统限流。
> - 后台任务进程退出。
> - 结算导出失败。
> - 部分任务成功、部分任务失败。
> - 服务恢复后积压任务重放。
> 
> 恢复后必须确认没有重复入账、重复审批或丢失关键任务。
> 
> ---
> 
> # 第五部分：开发实施计划
> 
> 建议以能力闭环为单位实施，而不是按照页面数量分配开发任务。
> 
> 以下阶段是建议的交付顺序，不代表未经代码盘点就能保证在特定周数内完成。
> 
> ## 阶段 0：现状盘点与架构决策
> 
> ### 目标
> 
> 确认现有代码哪些可以复用、哪些需要重构，以及现有模块之间是否真正打通。
> 
> ### 交付物
> 
> 1. 当前架构图。
> 2. 数据模型与关键关系图。
> 3. 核心业务流程图。
> 4. API 与后台任务清单。
> 5. Agent 与工具权限清单。
> 6. 测试覆盖率报告。
> 7. 数据迁移及兼容性方案。
> 8. 未关闭的架构决策清单。
> 
> ### 完成条件
> 
> 能够指出每个核心业务对象的真实存储位置、写入入口、读取入口和状态转换逻辑。
> 
> 如果只是存在一个页面或接口，但没有被业务流程实际调用，不应判定为已完成。
> 
> ## 阶段 1：规则引擎与金额账本
> 
> ### 目标
> 
> 首先建立可复现、可审计的金额计算内核。
> 
> ### 交付物
> 
> - 规则版本管理。
> - 规则校验。
> - 计算运行记录。
> - 输入快照。
> - 金额账本。
> - 独立对照实现。
> - 计算差异报告。
> - 历史结果回放。
> - 退款与冲销测试。
> 
> ### 完成条件
> 
> 所有 P0 规则测试通过，重复计算结果一致，规则版本与历史账本关联正确，关键异常可以阻止结算。
> 
> ## 阶段 2：证据图谱与数据质量
> 
> ### 目标
> 
> 使多源业务数据可以可靠地转化为正式绩效与激励流程的输入。
> 
> ### 交付物
> 
> - 来源事件标准化。
> - 事件去重。
> - 证据验证状态。
> - 数据质量问题管理。
> - 证据来源追溯。
> - 历史更正。
> - 下游影响识别。
> 
> ### 完成条件
> 
> 可以从正式计算结果追溯到原始事实；数据更正后能够定位受影响的下游对象；重复同步不会重复产生业务效果。
> 
> ## 阶段 3：贡献归属、评价与申诉
> 
> ### 目标
> 
> 建立事实、贡献、评价和员工反馈之间的明确边界。
> 
> ### 交付物
> 
> - 贡献申报。
> - 贡献认定。
> - 评价草稿。
> - 正式评价决定。
> - 人工确认。
> - 员工申诉。
> - 独立复核。
> - 评价版本与审计记录。
> 
> ### 完成条件
> 
> AI 评价不能自动成为正式结果；员工申诉不会覆盖原始记录；贡献认定具有完整依据；评价变更能够触发适当的下游复核。
> 
> ## 阶段 4：Agent Runtime 与主动工作流
>

> # 最终验收原则
> 
> 系统是否成功，不应以 AI 数量、Agent 数量或功能页面数量衡量。
> 
> 应以以下结果衡量：
> 
> - 数据是否可信。
> - 贡献是否有据可查。
> - 评价是否可以解释、复核和申诉。
> - 金额是否准确且可复现。
> - Agent 是否真正完成任务闭环。
> - 权限是否可控。
> - 异常是否能够安全恢复。
> - 历史结果是否可以审计。
> - 人工是否能够接管。
> - 系统是否可以在不依赖 AI 的情况下完成关键业务。
> 
> 只有当这些条件成立，Anari 绩效与激励 OS 才真正从一个 AI 辅助工具，升级为可用于正式业务决策的绩效与激励系统。

## 我的最终判断

目前，V3.1 的产品和工程设计已经可以形成一份相对完整的开发依据。但这里必须区分两个结论：

- **设计层面：** 可以继续收敛，不需要再无限增加概念和模块。
- **现有代码是否已经具备实施基础：** 还不能仅凭 PRD 判断，需要实际检查代码、数据库、API、后台任务和测试。

尤其是这三个问题，必须在进入大规模开发前回答：

1. **规则引擎是否真正独立于 AI？** 如果金额计算、规则判断和 Agent 逻辑仍然耦合在一起，应该优先拆分。
2. **证据是否真正贯穿到最终结算？** 如果数据进入系统后无法一路追溯到贡献、评价和金额，继续增加 Agent 只会扩大错误传播范围。
3. **Agent 是否具备真正的执行闭环？** 如果它只能生成建议，不能创建任务、跟踪状态、验证结果和恢复失败，就还不是完整的 Agentic 工作流。

**我建议下一步进入“代码与 PRD 的实施差距审计”，而不是继续扩写 PRD。**

以当前 V3.0 为基线，逐项核对已有代码，形成一张明确的差距表：

`需求 → 现有实现 → 调用链 → 测试证据 → 缺陷 → 改造任务 → 验收标准`

这样才能判断哪些模块可以保留、哪些必须重构、哪些尚未实现，并最终给开发人员一份可以直接执行的整改清单。

- 订单最终亏损，也不一定代表所有参与者的工作都做得不好。

## 三、系统需要什么样的项目管理能力？

这是本次 PRD 中一个重要的产品决策。

我的建议是：

**不必另建一个完整的项目管理系统，但必须建设工作包、交付验收和贡献归属能力。**

原因是，通用项目管理系统主要解决“任务如何安排和推进”；绩效与激励 OS 需要进一步解决“任务完成后，谁的哪些贡献可以被认定，如何进入评价和激励”。

两者有关联，但不是同一个产品。

建议的架构如下：

| 系统或模块 | 主要职责 |
|---|---|
| CRM / 商务系统 | 客户、商机、订单和商务过程 |
| ERP / 财务系统 | 订单履约、成本、回款、毛利等业务事实 |
| 飞书任务与审批 | 日常任务、协作、审批和通知 |
| PingCode / Gitee 等 | 需要时提供研发任务、代码和交付证据 |
| **N-Perform 贡献工作台** | 将订单、工作包、人员、交付、证据、验收、贡献认定和激励规则关联起来 |

首期应优先接入现有系统，而不是重复建设 CRM、ERP 和任务管理工具。

如果试点发现飞书等现有系统无法记录关键的责任分配、交付物、验收标准、依赖或范围变更，再在 N-Perform 中补充轻量工作包模块。

## 四、真正决定评价是否可信的，是工作如何被记录

我建议每个需要进入绩效或激励的工作包，至少具备以下信息：

- **目标与范围：**要解决什么问题，交付什么成果。
- **责任分配：**谁主责，谁协作，各自承担什么。
- **验收标准：**什么条件才算完成，谁负责验收。
- **时间与依赖：**承诺时间、实际完成时间、上游依赖和阻塞原因。
- **实际交付：**最终产生了什么文件、方案、产品、问题解决结果或业务成果。
- **证据来源：**来自哪个系统、哪条记录、哪个版本。
- **变更记录：**任务范围、期限、人员或验收标准发生变化时，为什么变化、由谁批准。
- **业务关联：**工作成果与哪个订单、客户、交付节点或业务结果有关。

例如，采购人员按时完成供应商筛选、降低了采购成本，相关证据就可以与订单、采购记录和最终成本关联。

如果技术支持解决了影响交付的关键技术问题，也应该有对应的技术问题、解决方案、验证结果和交付关联记录。

这样，评价就不必完全依赖员工月底自述，也不必让 AI 从大量聊天记录中猜测谁贡献最大。

## 五、AI 在其中究竟负责什么？

我不建议让 AI 直接给出“销售贡献 50%、采购贡献 20%、产品贡献 15%、技术支持贡献 15%”这样的数字，再把它当作客观事实。

AI 更适合负责：

1. 自动关联订单、任务、交付物和相关业务记录。
2. 发现工作包没有负责人、缺少验收标准或缺少交付证据。
3. 根据事前承诺和实际结果，生成个人贡献评价草稿。
4. 找出支持证据、反面证据和无法确定的部分。
5. 提示可能存在的重复计奖、贡献遗漏或不合理归属。
6. 将待确认事项分派给责任人，跟踪补证、验收和复核。
7. 根据实际运行结果，提出指标、评分标准和制度的改进建议。

但正式贡献认定仍需有权限的人确认；正式金额由确定性规则引擎计算。

这里还有一个重要原则：**证据可信度不等于贡献大小。**一条可靠的 ERP 记录能够证明某项业务事实发生过，却不一定能证明某个人对最终结果贡献了多少。

## 六、最后一个关键点：我们不能假装所有贡献都能精确量化

有些工作可以较准确地量化，例如销售回款、采购成本节约、交付准时率。

另一些工作，例如解决复杂技术问题、提前发现风险、帮助其他部门排除障碍，可能很难直接折算成一个客观数字。

因此，系统需要允许：

- 有明确证据、能够可靠量化的贡献，按配置规则计算。
- 有证据但难以直接量化的贡献，使用明确的评分标准和人工校准。
- 证据不足、归属存在争议的贡献，标记为待确认，而不是强行计算。
- 无法可靠归因的业务结果，保留不确定性，不伪造精确的个人贡献百分比。

这不是系统能力不足，而是为了避免 AI 生成看似精确、实际缺乏依据的评价。

**最终建议：先建设“贡献可追溯的绩效与激励 OS”，不要先建设一个庞大的项目管理系统。**先选择一类真实的跨部门订单，把订单、工作包、交付、贡献认定、绩效评价和激励计算完整跑通，再根据实际数据决定是否需要增强任务管理能力。

# 四、多人订单贡献算法：先建立事实，再进行评价

这是整个产品中最需要谨慎设计的部分。

我建议将贡献评价分成以下步骤：

1. **建立上下文：**订单、工作包、责任人、协作者、事前承诺和适用评分标准。
2. **验证证据：**检查来源、完整性、时效、冲突和更正状态。
3. **判断履约：**比较原始承诺、经批准的变更、实际交付和验收结果。
4. **识别影响：**判断交付对成本、交期、风险、客户体验等产生了什么影响。
5. **生成评价草稿：**AI 提供支持证据、反证、缺口和不确定性。
6. **人工认定：**授权评审人确认或修改，争议由独立人员复核。
7. **制度映射：**将正式认定映射到岗位绩效、团队指标或专项奖励。
8. **确定性计算：**规则引擎依据批准的结果和财务事实计算金额。

这里不建议设计一个通用的“订单贡献百分比算法”。

系统可以帮助企业认定每个人的具体贡献，但不能保证所有贡献都能被精确量化。

对于难以直接量化的工作，应采用有明确行为描述和证据要求的评分标准，而不是让模型凭感觉生成分数。

# 五、规则引擎要作为独立的核心领域模块

这部分不能使用 LLM 计算正式奖金。

建议设计一个受限的规则 DSL，由白名单运算组成，例如：

- 条件判断。
- 阶梯计算。
- 加权计算。
- 资格判断。
- 封顶和保底。
- 比例分配。
- 预算限制。
- 舍入规则。
- 币种转换。
- 冲销与调整。

每次计算都要记录：

- 使用的规则版本。
- 输入数据快照。
- 参与计算的评价结果。
- 资格判断过程。
- 中间计算步骤。
- 舍入和币种处理。
- 最终金额。
- 独立对照结果。

**正式计算与独立对照实现必须采用不同的计算实现路径。**

如果两者产生差异，就阻止结算并进入核查流程，而不是让系统自动选择其中一个结果。

# 六、Agentic 能力：从 AI 助手升级为可恢复的工作流执行系统

我不建议一开始就追求完全自主的绩效 Agent。

更合理的路线是：

| 阶段 | Agent 能力 |
|---|---|
| 第一阶段 | 读取证据、整理信息、生成草稿 |
| 第二阶段 | 主动发现缺失、冲突、逾期和重复计奖风险 |
| 第三阶段 | 创建待办、请求补证、指派处理人、追踪任务 |
| 第四阶段 | 验证处理结果、重试失败任务、升级长期阻塞 |
| 第五阶段 | 分析评价偏差、申诉原因和制度问题，提出改进建议 |

Agent Runtime 必须具有任务 ID、幂等键、权限校验、失败重试、超时、人工接管和完整审计。

特别是，Agent 不能因为工具返回成功，就认定业务动作已经完成。它必须检查实际的业务后置条件。

例如，Agent 发起了工作包验收请求，必须进一步验证请求是否成功创建、负责人是否正确、状态是否进入预期状态。

建议按八个阶段实施：

1. **架构与制度盘点：**确认首个试点、真实业务数据、指标定义、证据来源和规则样例。

5. **绩效评价与规则引擎：**建立 Rubric、评价流程、DSL 和金额账本。
6. **审批、申诉与结算：**完成完整的业务闭环。
7. **Agent Runtime：**逐步加入主动发现、任务创建、追踪和恢复。
8. **影子周期与正式试点：**与人工结果对账，验证可靠性后再启用真实结算。

不建议在数据事实层尚不可靠时，先投入大量精力开发复杂 Agent。

如果数据不准确，Agent 只会更快地产生看似合理、实际上缺乏依据的结论。

## 三、下一步不是继续堆文档，而是验证模型

我建议进入 **V1.1：核心模型验证与工程基线冻结**，优先完成以下工作。

### 1. 验证数据库和接口

- 在实际使用的 PostgreSQL 版本上执行迁移脚本。

### 2. 用真实订单验证多人贡献模型

这是本项目最需要优先验证的业务设计。

选择 5–10 个真实的跨部门订单，覆盖销售、技术支持、产品、采购等角色，验证：

- 每个订单如何拆分为工作包；
- 如何定义责任人和预期交付物；
- 哪些业务记录可以成为有效证据；
- 如何处理支持证据与反证；
- 如何认定多人贡献；
- 贡献认定如何进入绩效评价；
- 绩效评价如何映射到激励规则。

如果这一步发现模型不能准确表达真实业务，应先调整数据模型，而不是急于开始编写大量业务代码。

### 3. 再实现第一个端到端闭环

首个可运行版本不必一次完成所有 Agent。建议先打通：

**业务数据接入 → 证据标准化 → 工作包与交付 → 贡献申报 → 人工认定 → 绩效评价 → 确定性激励计算 → 审批 → 账本。**

随后再接入申诉、结算，以及能够自主执行任务的 Agent。
