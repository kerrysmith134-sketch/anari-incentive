# ADR-007: Operations SPA and statutory tax boundary

- **Status**: Accepted
- **Date**: 2026-10-30
- **Context**: The product needs a coherent operations surface rather than separate, hand-written HTML pages, plus a defensible implementation of China's progressive individual income tax. The API is the authority for roles, approvals and money, and the console must not grow a second source of truth. Statutory withholding has public brackets, but payroll runs currently use declared contract rates and do not aggregate year-to-date taxable income per person.
- **Decision**:
  - The console is a standalone React 19 + React Router 7 + Vite application in `apps/web`. It is built to `apps/web/dist` and served by Fastify under `/console/` behind the same CSP, request IDs and no-store policy as the API. Vite proxies `/api` during development. Client routes fall back to `index.html`; hashed assets are served by `@fastify/static`.
  - The console is a presentation layer only. It attaches the authenticated session headers, consumes the standard `{data, meta}` envelope, maps errors, aborts stale queries, and calls the existing API for every read and command. No approval, score acceptance, payroll transition or completion boundary is reimplemented in the browser.
  - A CSS token system is the design contract: semantic surface, ink, line, accent, status and spacing roles; selected light and dark palettes rather than automatic inversion; responsive sidebar-to-drawer navigation; native semantic controls with labelled fields and visible focus. The KPI layer uses stat tiles rather than decorative charts, and status is always expressed with text plus a marker rather than colour alone. No external UI or chart library is required.
  - The console exposes overview, approvals, payroll, rewards, integrations, AI assurance, policy, people and settings. Payroll tabs are deep-linkable via `?tab=`. Exports are fetched with authenticated headers and downloaded as blobs. AI score proposals can only be accepted or rejected by a human; the browser never performs an automatic decision.
  - `packages/payroll-tax` implements the public annualized China resident comprehensive-income cumulative withholding table with 3%–45% brackets, quick deductions, a ¥5,000 monthly basic deduction helper and BigInt fixed-point arithmetic. `POST /api/v1/tax/cn-iit/calculate` applies the bracket to cumulative taxable income and subtracts tax already withheld. The Tax studio shows the full bracket table and clearly labels the output as an estimate.
  - The calculator is deliberately not wired into payroll-run calculation yet. Payroll runs continue to use declared contract tax/social-insurance rates. Correct cumulative withholding requires year-to-date taxable income, special-additional-deduction evidence, prior approved/paid line aggregation and jurisdiction-specific filing data; presenting a declared-rate run as statutory withholding would be misleading.
- **Consequences**:
  - The console adds a second build artifact. Docker builds the SPA before starting the API; local development can run Vite and the API separately, or build once and use `/console/`.
  - Serving `/console/` from Fastify uses the existing development header authenticator locally and expects an OIDC-aware reverse proxy in production. The SPA is not an authorization boundary.
  - Browser tests and visual regression checks are not yet part of CI. Type checking and the production build are.
  - Progressive withholding remains an estimator until a payroll YTD aggregation model and statutory filing adapter exist. The public brackets may change; the bracket table lives in one package and is covered by boundary tests.
  - The console does not add charting, storage or offline capabilities, so it stays a thin, auditable client of the API.
